# SML 错误码

`codes.sml` 是 SML 全部错误码的**唯一事实来源**；`gen_json.py` 把它变成官网可读的
`site/static/errors.json`。官网的[错误码查询页](https://sml.swebase.cn/errors/)就是这个产物渲染出来的。

## 为什么要有错误码

在此之前，「同一个错误」在不同实现里是三句不同的话：

```text
Rust: 字段 `port` 类型应为 int，实际为 str（契约 `Server`）
JS  : 字段 port 类型错误：期望 int, 实得 str
C   : sml: 字段 `port` 类型应为 int，实际为 str（契约 `Server`）
```

文案一改，用户写的判断脚本就失效；想统计「哪类错误最多」也无从下手。
码把这两件事都解决了：**码是稳定契约，文案不是**。各端措辞可以不同（甚至不同语言），
码相同就是同一件事 —— 这也是跨实现统一（TODO 的 W3）的抓手：
先对齐码，文案差异就不再是问题。

## 形状

```text
E - CONTRACT - 002
│   │          └─ 序号：三位，只增不改；删掉的留空位，不回收
│   └─ 领域：见下表（14 个）
└─ 级别：E 错误 / W 告警 / I 提示
```

领域按**层**划分。分层只影响落地顺序，不影响码的稳定性 —— 任何一层的码都是对外契约：

| 层 | 领域 | 说明 |
|---|---|---|
| 语言层 | `LEX` `PARSE` `CONTRACT` `INCLUDE` `LIMIT` `FEATURE` `EXT` | SML 语言与契约语义；**五端必须同码**，是 W10 的落地对象 |
| 宿主绑定层 | `IO` `INTERNAL` `DERIVE` | C-ABI、Lua 绑定、Rust 派生宏与 serde 桥 |
| 工具层 | `MIGRATE` `CLI` `LINT` | `smltools` 的命令行、迁入格式、lint 诊断 |
| 编辑器层 | `EDITOR` | VSCode 扩展与 LSP 桥 |

沿用本仓库既有先例：qsm 的 lint 已在用 `E-ID-001` / `W-ID-100` / `I-ID-200`。

## 码的落地进度（W10）

「表里有一条码」与「实现真的会报这个码」是**两件事**，分开记：

| 端 | 带码情况 | 怎么带 |
|---|---|---|
| **Rust** | ✅ 全量（语言层四 crate：`sml-lex` / `sml-parse` / `sml-contract` / `sml-include`） | 引用 `rust/sml-codes` 的**常量**；错误类型是 `SmlError`，`code()` 取码、`message()` 取文案，`Display` 把码缀在文案之后 |
| **JS** | ✅ 全量（解析器 + 契约校验 + 模式引擎） | `e.code`（`parseSafe` 亦返回 `code`）；码是**字符串字面量** —— 该文件要能单文件在浏览器里跑，不能 import 生成物 |
| **C**（原生，`c/sml.c`） | ✅ 全量（23 个码） | 用 `c/sml_codes.h` 的宏；**码作消息前缀**写进同一个 `err` 缓冲（`E-XXX-NNN 文案`），取码 `sscanf(err, "%15s", code)`；`err==NULL` 或 `errsz==0` 时**一个字节都不写**（W13 的性质，必须保住） |
| **C++**（原生，`cpp/sml.cpp`） | ✅ 全量（27 个码） | 同上口径；取码用 `err.substr(0, err.find(' '))`。码表声明含 `cpp` 的 27 条已逐条对齐（W18 补齐了 include 那 5 条：002/004/010/011 与 E-LIMIT-003） |
| **Lua** | ❌ **本仓库做不了** | `lua/` 下只有 `main.lua`（demo 入口）与 `lua/lib/sml.soup`，而 **`.soup` 是编译产物、源码不在本仓库**，`MANIFEST.json` 也没写源在哪。要动它得先回到 Soup 工程拿 `.tl` 源码 + `soupc` 重编回填 |
| **C-ABI** | ✅ 已带 | `sml_error.code`（粗粒度枚举，9 档，供 C 侧 `switch`）+ `sml_error.code_str[16]`（真实码）；`classify()` 改成**读码**而不是猜中文关键词 |
| **smltools** | ⏳ 只有文案（部分随 `Display` 显示出来） | 待办 |

两条最容易搞混的：

- **`status` 讲的是行为，不是带没带码**。所以 W10 落地完，`status` 不会自动变 `done` ——
  它只回答「各端报不报这个错、报得一样不一样」。
- **「同一条件多端同码」现在可断言到四端**：Rust ↔ JS ↔ C ↔ C++ 各有一份「触发条件 → 期望码」
  的用例（`rust/tests/error_codes.rs`、`js/probe-error-codes.mjs`、`c/test_codes.c`、
  `cpp/test_codes.cpp`），互不相交的部分按实现结构差异豁免，**交集部分逐一同码**。
  **Lua 缺位**（原因见上表）。
- **落地 W10 时发现：`impls` 字段有多处「声明与实现不符」** —— 声明了某端、但该端其实静默。
  已逐条核实并分开处理：真能补齐的补齐（`E-PARSE-001` / `E-LEX-004` / `E-INCLUDE-001` 等），
  补不了的把声明改正并写进 `note`（如 `E-IO-002` 目前**没有任何实现**报它，归 W16 判定）。
- **C++ 的 include 是"声明与实现不符"的重灾区**（W18 修）：`E-INCLUDE-002` 声明了 `cpp`，
  但实现里环检测的栈 push 完立刻 pop、**永远为空**，这条码实际不可能触发；`E-LIMIT-003` /
  `E-INCLUDE-004` / `E-INCLUDE-010` / `E-INCLUDE-011` 则根本没有对应实现，同一条件分别
  表现为「静默跳过」「报成 E-INCLUDE-001」「丢弃子文件的词法错误」。
  教训：**`impls` 是claim，不是证据** —— 清点时看到某端在 `impls` 里，仍要实测它真的会报。
  **改码表前先实测，别按 `impls` 反推。**

## 加一条码

1. 在 `codes.sml` 的 `codes:` 数组里**末尾**加一项，序号接着当前领域的最大值往后排：
   ```sml
   { id: E-PARSE-011 domain: PARSE severity: E title: "新错误"
     msg: "规范文案（简短、无转义符）"
     impls: [ rust ] status: partial
     note: "为什么报、触发条件、与哪端不一致" }
   ```
2. 两个生成器都要重跑（两者都支持 `--check`，给 CI 用）：
   - `python errors/gen_json.py` —— 用**真实工具链**（`smltools --to json`）解析本文件，
     写坏了立刻报错；随后校验码的形状、唯一性、领域声明、级别与码前缀是否一致。
   - `python errors/gen_codes.py` —— 生成各端常量，并**反向校验**源码里手写的码字面量
     都在表里（挡住「手打错一位数字」这类编译器不管的错）。
3. 在实现里用它，并补一条「触发条件 → 期望码」的用例
   （Rust 加在 `rust/tests/error_codes.rs`，JS 加在 `js/probe-error-codes.mjs`）。
   **只加码不加用例等于没落地** —— 没人能证明它真的会被抛出来。
4. 提交。官网下次构建即自动更新（`site/build_site.py` 会先跑生成脚本）。

## 书写注意（本文件本身是 SML）

**所有文本值一律加引号。** 因为 `{`、`[`、`"`、`:`、`/`（连写成 `//`、`/*`）在 SML 里都是
结构字符，裸写会把一个值切成好几段 —— 这不是洁癖，本表第一版就因为这个被工具链拒了三次：

- `msg: 未闭合的块注释 /* ... */（遇到文件结尾）` → `/*` 开启块注释，整段被吃掉；
- `msg: 字符串未闭合（缺少结束引号 "）` → 那个 `"` 开启了一个字符串；
- `msg: ... 缺少片段体 { ... }` → `{` 开启了块。

引号内也不要出现反斜杠与半角引号，免得又掉进转义。

## 清点（2026-09-18）

`codes.sml` 里的码是对全部实现**按语义条件清点**出来的产物。清点规则：同一条件在多端
出现只算一条；同一语义在 5 个函数里各报一次也只算一条（位置合并到该条的 `note`）。

清了这些范围：

| 范围 | 覆盖 |
|---|---|
| Rust | 主 crate（含 C-ABI）与全部成员 crate：`sml-lex`、`sml-parse`、`sml-contract`、`sml-include`、`sml-regex`、`sml-value`（含 serde 桥）、`derive`、`smltools` |
| JS | `js/sml.mjs`（唯一事实来源）+ 站点与编辑器侧四份副本（逐字节比对确认一致）+ 扩展自身 |
| C / C++ / Lua | 三端全部源码、头文件与绑定层 |
| 工具 | `smltools` 的命令行、迁入格式（JSON / TOML / YAML / XML）、`--lint`、highlight 定制 |
| 编辑器 | VSCode 扩展与 LSP 桥 |

### 该报错却静默通过（清点的副产物）

清点时专门记了「该报错却静默通过」的地方。它们**没有码** —— 因为实现里根本没有这个错误，
给它们编号等于给「不存在的东西」发护照。记在这里是为了让 W3/W10 有据可依：

| 实现 | 静默点 |
|---|---|
| JS | 未闭合字符串 / 未闭合块注释 / 未知转义 / 闭合符错配 / 多余结束符号 / 顶层标量；未注册指令**带**片段体时被当成片段定义；未定义片段引用被当普通键；`env`、`contract`、`fragment` 等特性**无门控**（只有 include 做了）；模式匹配无步数预算 |
| C / C++ / Lua | 未闭合字符串（C、Lua）、未闭合块注释（C、C++、Lua）、顶层标量（三端都只在注释里陈述该限制）；**C 的数组元素不支持嵌套数组** —— `parse_array` 不递归，遇到 `[` 直接跳过，嵌套数组被**静默丢弃**（与 JS 早先修掉的「嵌套数组静默截断」同类，见 TODO 的 W17） |
| Rust | `sml-regex` 的非法或超长模式一律「不匹配」，无任何诊断；常规解析入口**丢弃诊断**（弃用告警用户看不到）；`sml-value` 序列化在深度超限时静默降级为占位文本；serde 桥把超出 i64 的 u64 静默变成浮点（丢精度）；C-ABI 的 JSON 解析失败静默返回空 |
| 工具 | YAML 的未知转义宽松保留（与 YAML 规范不一致）；`--feature` 与解析器实际版本不一致时只打提示 |

### 顺带查出的缺陷

清点按「错误点」扫，但扫的过程里撞上了几个**真缺陷**：它们的共同特征是「用户拿到的东西错了，
却没有任何报错」—— 正是错误码体系想消灭的那一类。都已单独登记到 `TODO.md`：

- **C++ 的深度守卫可被绕过**：`parse_block` 遇到子块时直接递归，不经过限深入口，纯块嵌套
  不增长深度计数 → 深嵌套可打穿栈，`E-LIMIT-001` 在该路径上形同虚设。**修的时候又发现
  更深一层**：光把「子块走受限入口」补齐还不够 —— 原来的守卫在超限后把深度**复位为 0**，
  而复位不会让已压上的栈帧退回来，外层循环随即又从 0 往下钻，「每 128 层一轮」反复压栈，
  10 万层照样崩。真正收手要靠一个**中止标志**让各层循环 break（Rust 侧等价问题当年是靠
  `Result` 的 `?` 向上传播解决的，两侧思路一致）。
- **C 也有同一个深度问题**：`parse_block` 是带守卫的 wrapper（审计时据此判定「C 无此洞」），
  但同样的「复位深度不能收手」让它**一样能被打穿** —— 实测 10 万层块嵌套段错误。
  结论：只看「有没有守卫」会漏，必须看**超限之后是否真的停止下降**。
- **C 的错误路径越界写**：版本错误分支把 1 字节的复合字面量当缓冲，却拿调用方给的 `errsz`
  作写入上限 → 调用方传「缓冲为空但大小大于 1」时会污染栈。顺带查出**同一类的更大一片**：
  `sml.h` 明写 `err` 允许为 `NULL`，而所有 `snprintf(errbuf, errsz, ...)` 的点在 `errbuf`
  为 NULL 时都是空指针写。两类现已一起收敛到统一的写入助手。
- **JS 空键列表抛 `ReferenceError`**：报告函数是另一个函数的局部量，那条分支引用不到它。
- **Lua 完全没有深度上限**：深嵌套会耗尽 C 栈（此前表里写「Lua 侧未确认」，现在确认是**缺**）。
- **C 的 JSON 桥静默失败**：失败直接返回空指针且不写 err，调用方无法区分「空结果」与「出错」。

## 纪律

- **码一旦发布就不再变含义**。要改语义就发新码，把旧码标成 `deprecated`。
- **同因同码**：同一触发条件在五端必须给同一个码。
- **序号只增**，不回收、不复用。
- `status: done` 表示「列在 `impls` 里的实现**都已经真的报这个错**」，`partial` 表示各端行为
  不一，差异写在 `note` 里。注意它描述的是**行为是否已实现**，与「是否已经带上码」无关 ——
  后者是 W10 的活，进度见上面的「码的落地进度」一节。
- `coverage` 现在是「全量」：清点表里的每个错误点都有码。**新增错误点时同时补码并更新这行**，
  别让它变成一句空话。
