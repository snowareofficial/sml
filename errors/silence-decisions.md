## 2. 顺带查出的「声明与实现不符」（**必须先处理，否则判定表建在沙上**）

### 2.1 `E-PARSE-008`（顶层标量）——**没有任何实现报它**

- 码表写 `impls: [rust]`，W3 的行也写「四端一律显式报 `E-PARSE-008`」。
- **实测**：`42` 在 Rust 里 **OK**，而且被解析成 `{"42": 42}`（`--to json`）——
  即**又一类凭空造键**（与 W17 同族：静默把数据改成别的形状）。
- **根因**：`E_PARSE_008` 在 `rust/` 里只出现在**常量定义 + doctest + README 示例**，
  没有一处 `SmlError::new(E_PARSE_008, …)` 落点 ⇒ 这条码**从未被接线**。
- 结论：W3 的前提不成立。要么真实现它（五端一致报错），要么改正 `impls` 并写进规范。

## 3. 需要你拍板的四件事

**Q1：B 组要不要整体做？**（JS 11 条全静默、C 1 条、Lua 2 条）
- 选项①：**全做**（与 Rust 同码）—— 一致性最好，但一批现"能解析"的文档会开始报错，需进 CHANGELOG 的不兼容/行为变更段。
- 选项②：**只做"静默改数据"那几条**（B4/B5/B7 + A 组）—— 优先堵住"数据被悄悄改错"，LEX 那族（B1–B3）先写进规范。
- 选项③：**只写进规范**，不改实现 —— 保持现状，把"某端宽松"变成白纸黑字。

**Q2：`sml-regex` 非法/超长模式静默「不匹配」怎么办？**
- 我倾向**报错**（用户会以为"模式不匹配"，实际是模式写错了）。映射可用 `E-LIMIT-007`/`E-LIMIT-009`（JS 已有）之类，或新增一条 `E-MIGRATE`/`E-EXT` 域的码 —— **新增码要你点头**。

**Q3：YAML 未知转义收紧到规范吗？**（现在宽松保留）
- 收紧 ⇒ 拒掉现在能读的 YAML（`E-MIGRATE-013`）；不收紧 ⇒ 在规范里写明"比 YAML 宽松"，并把它从静默清单移到"有意行为"。

**Q4：`&undefined` 到底是「未定义片段引用（该报错）」还是「普通字符串（合法）」？**
- 这取决于 SML 的**规范意图**。Rust 报 `E-INCLUDE-006`；若你认为 v1 语义下它该是普通字符串，那要改的是 **Rust**（它报错了），而不是让另外三端跟着报。

> 判定完成后：把结论回填 `errors/README.md` 的清单（每条标注「改成报错（码 X）」或
> 「规范允许静默」），再按 §1 的实现清单动手；`E-PARSE-008` 那条要单独进 CHANGELOG。

### 4.1 A1 / A2（JSON 桥失败不写进 err）的口径说明

`sml_parse(text, err, errsz)` 的**每条**失败路径现在都会带码（含新的词法错误与兜底
`E-PARSE-012`）。但 `sml_parse_json(text)` 的签名**没有 err 槽位**（`char *sml_parse_json(const char *)`
是公开 API），调用方只能靠「返回 NULL」判断失败、看不到具体码 —— 要改就得加/改公开接口，
属对外接口变更，**需用户拍板**，故本批未动。同理 `sml_dump_from_json`。

### 4.2 A3–A6（serde 保真 / 序列化深度 / 诊断出口 / JS 步数预算）

都在别的实现层（`rust/sml-value` 的 serde 桥与序列化、JS 模式引擎），**不在 C 批范围**，
留给 Rust 侧那 6 条与 JS 余额一起做。
