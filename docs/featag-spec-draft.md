# featag 规范草案 v1.0（**语义已闭合 · v5 门槛 · 零实现**）

## 0. 一句话

**featag = 挂在块头上的「带参数标签」**：契约处**声明**（`!name` / `!name: 类型`），
块头处**实例化**（`!name` / `name[值…]`），解析器只把它落成**数据**，语义由应用层解释。

心智模型 = **Rust 泛型**：契约是「类型定义 + 泛型参数表」，块头是「实例化处」。
⚠️ 唯一不成立的一点：Rust 是**编译期单态化**，featag 是**数据 + 应用层解释**。

## 1. 目标 / 非目标

**目标**

1. 让「类型 + 少量参数」在块头里紧凑表达（`rectangle size[2], btn1 { }`）；
2. 无参数标签零成本（`service api !critical !tls, prod { }`）；
3. 核心只负责**结构**，不承担宏语义 —— 「解释」属于应用层。

**非目标（明确不做）**

| 不做 | 理由 |
|---|---|
| **用 featag 表达「改写已有键」** | 用户原话「它不能用于覆盖，这会搞出乱子，SML 规范应该明确避免」。 ⚠️ 语言层能管的只有**语法**：参数只能是**值**，不能写成「目标键 → 新值」（见 §6） |
| 规定**谁**执行填充、或「必须填充」 | 用户 2026-11-03：「应用层那就不一定是填充了」⇒ 语言只把**落点规则写成数据**（§6.1），执行与否、由谁执行**不指定**；不实现的端忽略落点即可 |
| 改写 `__*` 元数据 | 见 §6，正文手写 `__*` 一律**显式拒绝** |
| 编译期展开 / 单态化 | 与「纯数据 + 应用层」冲突 |
| 替代 `&frag` / `@when` / `@for` | 见 §9 边界表 |

## 2. 语法（仅 v5）

### 2.1 声明（写在契约体内，记号与使用处一致）

```sml
@contract wea {
  a: int
  !critical              # 无参 featag（无落点 = 纯标签）
  !obey: [int]           # 带参 featag（参数类型 = 契约字段类型语法）
  !tls: [str] -> tls     # 带落点：参数落到 `tls`
  !cert: str -> tls.cert # 落点可以是**点路径**
}

# 字段的写入来源（见 §6.2）：只能由 featag 写，文档里直接写该键 ⇒ 报错
@contract Tls {
  cert: str from-featag
  key:  str from-featag
}
```

- 不用新指令，也不做 `@contract { } impl { }` 两段式（用户 2026-11-03 取「②」）：
  `impl` 属宏行为，塞进 `@contract` 会让五端必须「忽略」或「报错」`impl` 段，两头都不干净。
- featag 名**契约私有**（§5），诊断必须写全 `wea.critical`。

### 2.2 使用（块头）

```sml
wea name { }                        # 无 featag：与今天逐字一致
wea !critical, name { }             # 一个无参 featag
wea !critical obey[1, 2], name { }  # 一个无参 + 一个带参
wea !critical obey[1, 2], { }       # 块名可省
```

- `!` = featag 区开始，**按词首前缀判定** ⇒ **词法零改动**（实测 `!critical` 今天是一个裸词）；
  ⚙️ **性能**：判据就是「词首字符是否 `!`」，与现有首字母判断同量级、**不引入新扫描**；
  实现后若基准有可见变化，按用户要求「影响大就问」，先报数字再动；
- `[ ]` = 参数值，**方括号本来就是 token**（不用 `( )`：实测 `obey( 1, 2 )` 会直接报
  `E-PARSE-007`，加括号 token 属破坏性词法变更）；
- `,` = featag 区**终止**（今天在裸词位置本就是错误 `E-PARSE-007` ⇒ 零冲突）；
- featag 区内**不再用逗号分隔**各项（`,` 只作终止符）；
- **参数值一律写 `[ ]`**（标量也是 `size[2]`）：`!` 之后的裸词位置只放 featag 名，
  这样「名字 / 值」不可能混读；
- `[ ]` 内可含逗号与嵌套，**只有括号深度 0 的 `,` 才终止**。

### 2.3 歧义一律报错，不猜（2026-11-03 定）

用户原话：「歧义，建议报错，要求加双引号」「b3 参考 b2 我的回答」「b4 好的」「b5 暂时是」。

| # | 情况 | 处理 |
|---|---|---|
| B1 | **空 featag 区**：`wea ! , name { }` | **报错**（`!` 后必须至少一个 featag 名） |
| B2 | **值位置**出现以 `!` 开头的裸词（`a: !b`） | **报错**，要求写 `"!b"`。⚠️ **即使开了 `bareword-string` 也不豁免** —— 歧义就报错，不靠特性绕过 |
| B3 | **块名**以 `!` 开头 | **报错**（同 B2 的精神；块名无法加引号，故直接拒） |
| B4 | **声明处**重复 featag 名（两个 `!obey`） | **报错**；使用处允许重复（数据里保留顺序） |
| B5 | `auto` | **暂时**只在 featag 参数槽有特殊含义（= 取声明里的默认值）；别处仍是普通裸词。将来若要全局保留，另立一笔 |

⇒ 一句话：**`!` 只在「块头契约名之后」这一处被当成记号，其它位置出现即歧义即报错。**

## 3. 数据形状

```sml
wea !critical obey[1, 2], name { a: 1 }
```

落成（**已定** —— 见 §10 Q1）：

```sml
{ wea: { __featags: [ { name: "critical" }, { name: "obey", args: [1, 2] } ], a: 1 } }
```

- **保序数组**（不用映射）：允许同名 featag 出现多次（应用层自行决定是否合并），且不丢顺序；
- 不复用 `__args`：`__args` 今天的含义是「块名之后的裸词」，两种语义混在一起会分不清。

## 4. 参数类型

白名单（与契约字段同一套语法）：

| 类别 | 具体 | 备注 |
|---|---|---|
| 内置标量 | `str` `int` `num` `bool` `enum` | `BUILTIN_TYPES` |
| `any` | 允许，**默认禁用**；开关在**契约级**（契约内写 `!any`，见 §10 Q7），**不是文档级特性位**，也不要求全局一个开关 | 等于放弃校验 |
| 复合 | `[T]`、`{ … }` | |
| 文档自定义 | `@type` 声明的类型 | |
| 库注册 | `TypeCheck` 外置类型（`image` / `link`…） | |
| **契约引用** | `Point`（单值）与 `[Point]`（数组，2026-11-03 用户**允许**） | `[Point]` 的 Lua 支持是**单独一笔工作**，不在本规范范围 |
| 修饰符 | `optional` `required` `default` `min` `max` + 外置 7 个 + **`from-featag`**（§6.2） | |

**递归契约引用：允许。** 两条护栏：

1. 深度上限沿用 `MAX_VALUE_DEPTH`（129 层报 `E-LIMIT-001`），不另设限；
2. **默认值不得是容器类型**（今天事实上如此：`default {}` 报 `E-PARSE-021`），
   要写成规定 —— 否则「环 + 容器默认值」会无限填充。

实测依据：`A { b: B }` / `B { a: A }` + 有限数据 ⇒ 正常报
`E-CONTRACT-003 必填字段缺失：字段 b.a.b.a.b.a`（不崩，校验只跟着数据走）。

## 5. 作用域

**契约私有**。`wea.critical` 与 `other.critical` 互不干扰（同 Rust 泛型参数名只在类型内有效）。
⇒ 所有诊断与文档必须写全 `<契约>.<featag>`。

## 6. 禁止覆盖 / 保留键

「禁止覆盖」要分成两件事，**只有第一件是语言能强制的**：

| 层级 | 规则 | 谁来强制 |
|---|---|---|
| **语法（语言）** | featag 参数只能是**值**（标量 / 数组 / 对象字面量），**不能表达「把某个已有键改成某值」** —— 没有「目标键」这个语法位置 | 解析器，五端一致 |
| **解释（落点规则，§6.1）** | 语言把「参数 → 哪个键」写成**数据**（`-> 路径`）；补缺、覆盖报错、父对象自动创建等规则由规范定义 | 规则由规范定义；**执行者任选**（不实现的端忽略落点，不报错） |

⚠️ 为什么必须这么分：解释方式既然开放（§1），语言就**没有资格**规定「应用层能不能覆盖」——
但语言**可以**保证「文档里写不出这种意图」，这正是第一行。

- **正文手写 `__*`（`__type` / `__name` / `__args` / `__featags`）⇒ 显式拒绝**。
  实测依据：今天 `wea { __type: "other" a: 1 }` **原样保留**手写值 ⇒ `__type` 可被伪造，
  一旦它参与「用哪份契约」的判定，文档就能自己换校验规则。

## 6.1 落点规则（**B 档：填充规则写在 SML 里**，2026-11-03 定）

声明处用 `-> <落点>` 指出参数落到哪个键。**规则本身是数据，不是代码**，
于是任何实现（含五端）执行同一份文档应得到同一结果 —— 这是 A 档（规则留在应用层）做不到的。

```sml
@contract service {
  !any
  !critical                  # 无落点 = 纯标签，只进 __featags
  !tls: [str] -> tls         # 参数落到同名字段
  !cert: str -> tls.cert     # 多参数拼出对象形状：两个 featag 各占一条路径
  !key: str  -> tls.key
}

api !critical cert["c.pem"] key["k.pem"], web { name: api }
```

填充结果（`tls` 原本不存在 ⇒ 按路径建出来）：

```sml
api: { tls: { cert: "c.pem", key: "k.pem" }, name: "api" }
```

**规则（全部可判定，无表达式）**

| # | 规则 |
|---|---|
| 1 | **落点已存在 ⇒ 报错**（禁止覆盖，不静默跳过） |
| 2 | 落点不存在 ⇒ 写入参数值 |
| 3 | 落点路径上的**父对象不存在** ⇒ **默认自动创建**（否则路径没有意义；这是「插入」不是「覆盖」）。<br>契约级开关 **`!strict-paths`** 可关闭：开启后父对象必须已存在，否则报错 |
| 4 | **无落点** ⇒ 纯标签，只留在 `__featags` |
| 5 | `auto` ⇒ 用声明里的默认值作值 |
| 6 | 路径**可穿对象，也可用 `[n]` 穿数组**（2026-11-04 用户定「数组建议是做一个」）：<br>· `n` 必须是非负十进制整数；<br>· **越界即报错，绝不补 null**（与 `docs/null-semantics.md` N1–N5 一致）；<br>· **不支持 push 形式 `items[]`**（会破坏填充幂等：同一文档填两次数组变长两次） |
| 7 | **键名不得含 `.`（且建议一并禁 `[` `]`）** —— 于是路径分段**永远无歧义**，<br>「键名自带 `.` 取不到」这个老坑从根上消失（用户 2026-11-04：「键名不能带 .」） |
| 8 | **明确不做**：条件、循环、插值、改写已有值、由多个参数拼出计算值 |

⚠️ 与既有约定的耦合：第 5 条 + 「默认值不得是容器」+ 递归契约引用，三者一起才保证不会无限填充。

## 6.2 键的写入来源：`from-featag`（2026-11-03 定）

字段上可加修饰符 **`from-featag`**：**该键只能由 featag 落点写入**；文档里直接写它 ⇒ 报错。

```sml
@contract Tls {
  cert: str from-featag
  key:  str from-featag
}

api !cert["c.pem"] key["k.pem"], web {
  cert: "fake.pem"        # ⇒ 报错：来源非法（这个键只能由 featag 给）
}
```

**为什么只有这一档，没有 `none` / `readonly`**：用户 2026-11-03 定
「**v5 会尽可能减少 null / none 思维**」。所以不引入第三种来源值 ——
「一个键谁也写不了」这种需求本来就不该靠修饰符表达：

- 该键**必填**却没有任何 featag 提供它 ⇒ 校验期自然报 `E-CONTRACT-003`（缺字段）；
- 该键可有可无 ⇒ 写 `optional`。

⇒ 二档足够：**默认（谁都能写）** / **`from-featag`（只能 featag 写）**。

⚠️ 这条也是「外来数据不可伪造」的语言级抓手（可与 I-24 外来数据安全一并做）：
`from-featag` 的键，文档无法自行赋值，也就无法伪造。

## 7. 可裁剪 / 模块化（用户 2026-11-03 要求）

> 用户原话：「可裁剪、模块化，我说的是**对不同版本的支持**，底层其实是一个个 feature。」

所以裁剪的单位是**版本**，不是「功能开关」：

| 层 | 内容 | 开关 | 关掉后 |
|---|---|---|---|
| **版本支持** | 每一代语法各一个 feature（`v1`…`v5`） | cargo feature（编译期） | 该代语法不支持：能编掉解析分支、码表与文案也不进产物 |
| **L-声明校验** | 契约里 `!name`、未声明即拒、参数类型校验 | SML 特性位 **`type.featag`**（命名空间见 `docs/feature-namespace-plan.md`） | 只保留 `__featags` 数据，不校验、不报错 |
| **L-解释** | 填充/展开（应用层） | 调用方注册（外置 impl / `ParseOptions::directive`） | 核心零代码、零文案 |

- **`any` 可细分启用**：不必全局一个开关（可到「某契约 / 某字段或参数」一级，粒度见 §10 Q7）；
- 新增 SML 特性位**只追加、不改已有位序**（C-ABI `sml_feature_name(bit)` 依赖位序稳定）；
- ⚠️ **特性命名空间**（用户点名，v5 新增）：v5 引入的特性名不能与 v1–v4 已有名撞车，
  需要一层命名空间（如 `v5/any` 与 `any` 分开），否则 `@feature enable any` 在 v4 文档里含义会漂移（见 §10 Q8）。

## 8. 版本门槛

**v5 的定义（用户 2026-11-03）：crates.io 上最后一个 stable 之后引入的语法，全部算 v5。**
⇒ 不需要逐条判断「这个改动算不算破坏性」：只问「它是否已在 stable 里」，不在就是 v5。

| 版本 | 行为 |
|---|---|
| `v1`–`v4` | 现状逐字不变：`!critical` 仍是裸词（会被当字符串/报 `E-FEATURE-005`）、`__*` 仍可手写、`any` 仍可用 |
| `v5` | 启用本规范；`any` 默认禁用（可细分启用）；正文写 `__*` 报错 |

⇒ **依赖**：v5 门槛要先有版本判据（I-16 的版本表 + 各版本 feature），
否则「只在 v5 生效」落不了地。这一条应在 featag 动工前确认。

## 9. 与既有机制的边界

| 机制 | 职责 | 与 featag 的重叠 |
|---|---|---|
| `@is <契约>` | 应用契约（校验/默认值） | featag 不改变用哪份契约；**不得**借此改 `__type` |
| `&frag` | 行级拼接 | featag 是块头标签，不拼行、不改写正文 |
| `@when` / `@for` | 解析期条件/循环 | featag **不做**条件插入与展开（那是应用层的事） |
| `typed-block` / `contract` | 决定「裸块首词是否当契约」 | featag 的 `!` 区在裸块头之后解析，两者串行不冲突 |
| 字段默认值 | 契约级补缺 | featag 的「填充」只能**补缺**，不能覆盖（§6） |

## 10. 已定 / 未决

### 已定（2026-11-03 用户逐条回答）

| # | 决定 |
|---|---|
| **Q1** | 落点键名 = **`__featags`**（保序数组），不复用 `__args` |

| **Q8** | 特性命名空间 = **两段上限 `<域>.<名>`、只用于新增**（详见 `docs/feature-namespace-plan.md`，2026-11-03 已定稿） |
| **Q11** | 填充规则 = **B 档：写在 SML 里**（`!name: 类型 -> 落点`），规则是数据、任何实现执行结果一致 |
| **Q12** | 落点**允许点路径**（`tls.cert`）；只穿对象、不穿数组；键名自带 `.` 的字段不可作为落点 |
| **Q13** | 落点记号 = **`->`**（与 `include "x.conf" -> "x.sml"` 的 ext-rewrite 同形） |
| **Q14** | 父对象自动创建**默认开**、**契约级**开关 `!strict-paths` 可关（关闭后父对象必须已存在） |
| **Q15** | 键的写入来源 = 字段修饰符 **`from-featag`**（只能 featag 写）；**不做 `none` / `readonly` 档** |
| **Q16** | v5 原则：**尽可能减少 null / none 思维**（因此不引入第三档来源值） |
| **Q17** | 歧义规则 B1–B5（见 §2.3）：**一律报错、不猜**；`!` 只在块头契约名之后被当记号 |
| **Q18** | 落点**支持数组下标** `[n]`（越界报错、不补 null、无 push）；**键名禁止含 `.`**（老坑从根上消失） |
| **Q19** | 库代码**不得堆字符串**：关键字/保留词集中成常量，面向用户的文案一律走 `errors/codes.sml` 生成物 |

> ✅ **本草案 Q1–Q10 已全部定稿，当前无未决项。**

## 12. feature 命名空间（后续工作，用户 2026-11-03 提出）

> 用户原话：「之后还得整理一下 features，使用命名空间，但是**层数不能过多**。」

现状与约束：

- 现有 SML 特性名是**平铺裸词**（`bareword-string` / `typed-block` / `block-name` / `contract` /
  `include` / `fragment` / `env` / `when` / `for` …），且 `@feature enable <名字>` 里直接写；
- **C-ABI `sml_feature_name(bit)` 返回字符串**、且位序被 C 调用方依赖 ⇒
  **老特性名一个都不能改**，命名空间只能加在**新增**特性上；
- v5 会新增 `featag`，后续还会有更多 ⇒ 现在就得定规则，否则以后改名 = 破坏 C-ABI。

规则（**2026-11-03 已定稿**，完整版见 `docs/feature-namespace-plan.md`；下面只留摘要）：

1. **两段上限**：`<域>.<名>`（如 `v5.featag` / `type.any`），**禁止三段及以上**；
2. **只用于新增**：老名（`typed-block` 等）保持原样，不加前缀；
3. **域清单封闭**：域必须是**登记过的白名单**（不是随手命名空间），
   否则「层数少」也挡不住命名发散；
4. **单一事实来源**：一域一表，落在 `rust/sml-feature`（枚举 + 位序）+ `errors/codes.sml`（文案），
   生成物（C 头 / JS / Lua）跟着生成，不手抄；
5. **`!any` 不是特性位**：它是**契约级**开关（§10 Q7），不占 C-ABI 位 —— 位是稀缺资源。

⚠️ 这条与 featag 的关系：`featag` 只是第一个「v5 新特性」，**命名空间规则应在它之前定**，
否则 `featag` 会成为下一个「不能改名的老名」。
