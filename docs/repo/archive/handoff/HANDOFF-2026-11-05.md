## 3. 五条不变量（fuzz / bench 前必须先懂）

1. **未知段可跳过** —— 长度自描述，不许「读前先跑解释器」。
2. **签名签 `canonical_text`** —— 与 `fmt` 解耦，布局升级不失效历史签名。
3. **追加不改旧字节** —— `compact` 是唯一例外，且必须重签。
4. **键序是值层事实** —— `dump*` 只收 `&CanonicalValue`；无序值**编译期**就进不来。
5. **基文档绑进签名** —— `Layer.base_hash` 进 `signed_text`，换基文档当场被抓。

> 第 4、5 条是最近才补的，**fuzz 时最容易在这里发现"旧假设"**：
> 例如 `load` 出来的值一定是 `Ordered`（canonical 解码保证），
> 但 `pack` 的载荷不是 `Value`，两者不要混着断言。

## 4. fuzz 接入计划（**sml 系列 + smlb**）

### 4.1 现状：只覆盖了一个 crate

`rust/fuzz/` 是**独立 workspace**（nightly/libFuzzer，刻意不进 `cargo test --workspace`），
目前只有 **1 个 target**：

```
rust/fuzz/fuzz_targets/parse.rs      # 只 fuzz sml_parse::parse
```

**14 个成员 crate 里，其余 13 个零覆盖**，包括所有二进制入口（`smlb`）和
所有值层编解码（`sml-value`）。这是交接时最需要补的一块。

### 4.2 攻击面分层（先按「吃谁的字节」分组，再决定 target）

| 层 | 吃什么 | crate | 入口 |
|---|---|---|---|
| **L1 文本** | 不可信 SML 文本 | `sml-lex` / `sml-parse` / `sml-include` | `tokenize`、`parse` / `parse_with` / `parse_ordered` / `parse_file*` / `loads`、`parse_include_line` |
| **L2 字节** | 不可信 `.smlb` | `smlb` | `load` / `check` / `info` / `ls` / `payloads` / `parse_frame_index` / `verify` / `verify_chain` |
| **L3 值编码** | canonical 字节 | `sml-value` | `from_canonical_bytes` / `subtree_at` / `parse_strtab_table` |
| **L4 模式** | 正则 / 模式串 | `sml-regex` / `sml-pattern` | 编译与匹配（优先级低，但别忘） |

> L3 被 L2 间接覆盖，但**单独 fuzz 更快定位**：一个畸形 canonical 字节，
> 从 `smlb::load` 进去要穿过容器层才发现，从 `from_canonical_bytes` 直接进去就一眼看到。

### 4.3 建议的 target（按优先级）

| # | target | 覆盖层 | 为什么排这个位置 |
|---|---|---|---|
| 1 | `smlb_load` | L2 | 最外层攻击面：`load` / `check` / `info` / `ls` / `payloads` |
| 2 | `smlb_get` | L2 | 路径解析 + 零拷贝切片，越界风险最高 |
| 3 | `value_canonical` | L3 | 上游，定位快；且 `load` 也走它 |
| 4 | `parse_variants` | L1 | **扩展现有 `parse.rs`**，不是新写（见 4.4） |
| 5 | `smlb_pack` | L2 | 写路径 + 载荷表 |
| 6 | `smlb_layer` | L2 | `verify` / `verify_chain`，签名安全核心 |
| 7 | `smlb_crypto` | L2 | AAD / nonce / 分块边界（固定 key） |
| 8 | `regex_compile` | L4 | 可选，吃模式串 |

### 4.4 现有 `parse.rs` 该怎么扩（不是重写）

它现在只喂 `parse(&str)`，漏掉了三条**逻辑完全不同**的路径：

| 漏掉的入口 | 为什么必须单独喂 |
|---|---|
| `parse_ordered` | 走 `Map::ordered()` 构造，与默认路径的容器行为不同 |
| `parse_with(ParseOptions)` | `collect_errors(true)` 会走「同层恢复」逻辑，是另一套状态机 |
| `parse_file` / `loads` | `include` 展开会读**外部文件**；fuzz 时用临时目录 + 把 include 目标也当 fuzz 输入 |

`tokenize` 也值得直接喂：`sml-lex` 是 `sml-parse` 的上游，词法层的 panic 会掩盖解析层的判断。

### 4.5 断言口径（不要只写「不 panic」）

每个 target 至少断言这四条，否则 fuzz 通过也没有意义：

1. **不 panic**：越界 / 截断 / 畸形 varint / 非法 UTF-8 都必须返回 `Err`。
2. **错误可分类**：`err.kind()` 必须非空且落在已知集合（不是 `""`）。
3. **不 OOM**：用全局计数分配器（照抄 `benches/perf.rs` 的 `count_allocs`）
   给单次输入设上限；解压炸弹靠 `DecompressTooLarge` 兜底，但 fuzz 要证明它真会触发。
4. **往返闭合**（L2 / L3 最强的一条）：
   `load` 成功 ⇒ `dump` 回同一值 ⇒ 与原文件**逐字节相同**。
   这一条能一次抓到「能解析但不能重写」的隐性 bug。

L1 的对应版本是：`parse` 成功 ⇒ `to_sml` ⇒ 再 `parse` ⇒ `eq_ordered` 相等
（**不是**字节相同——默认 `parse` 是无序的，见 §3 第 4 条）。

### 4.6 已经被测试钉住的防护（fuzz 去撞它们，而不是重写）

| 防护 | 位置 | 期望 |
|---|---|---|
| 截断段体 | `smlb::container` `TruncatedSegment` | `Err`，不 panic |
| 值深度 | `MAX_VALUE_DEPTH` | `Err`（`DepthExceeded`） |
| 解压上限 | `DecompressTooLarge { seg_id, limit }` | 按解压炸弹拒绝 |
| 路径穿越 | CLI `unpack` 拒绝 `..` / 绝对路径 / 盘符 | 命令层拒绝（库侧不写盘） |
| 重复载荷名 | `DuplicatePayloadName` | `Err` |
| 键序缺失 | `KeyOrderUnavailable` | 只在显式无序值时；`load` 产出的值不该触发 |
| 能力位 | `MissingCapability` / `BadCapabilityName` / `DuplicateCapability` | 读侧拒 / 写侧格式校验 |
| 基文档被换 | `base_hash` 比对 | `verify` 与 `verify_chain` 都必须失败并点名 |
| 解析错误数上限 | `collect_errors` 上限 64 | 不无限累积 |

### 4.7 看着像 bug、其实不是

- 空文件 / 只有 40 B 头 ⇒ `Err`（不是 panic）。
- 段表声明的 `len` 超过文件长度 ⇒ `TruncatedSegment`。
- 未登记的能力名**可写**（扩展通道），`check` 标「未登记」，不报错。
- 加密文件用错钥匙 ⇒ `auth-failed`（统一报错，不泄露 key 错还是 tag 错）。
- 非 SHA-256 摘要的流式写退化为「先读进内存」（见 §6）。
- 默认 `parse` 出来的对象是 `Unordered`，`dump` 会拒绝 —— 这是设计，不是 bug。

## 5. bench 接入计划（**sml 系列 + smlb**）

### 5.1 现状：只有一个 bench，只测解析

`rust/benches/perf.rs` 是**零依赖手写计时器**（刻意不引 `criterion`），
`docs/perf-baseline.md` 记录的是 small / large / deep 三组解析数字。
**值层、容器层、层链、加密全部没有 bench。**

### 5.2 建议拆成三个文件（别塞一个）

| 文件 | 测什么 | 理由 |
|---|---|---|
| `benches/perf.rs`（**已存在，不动**） | `parse` / `to_sml` / 分配数 | 历史基线已入库，改了会失去可比性 |
| `benches/value.rs`（新） | `to_sml` / `canonical_text` / `canonical_bytes` / `Value::get(path)` / `eq_ordered` | 值层是解析与容器之间的公共底座，单独看才看得出是谁慢 |
| `benches/smlb.rs`（新） | `dump` / `pack` / `load` / `get` / `mmap` / `Writer` / 解密 | 容器层指标自成一套（吞吐 + 堆增量） |

### 5.3 各组要测什么、报什么

| 组 | 输入 | 报什么 |
|---|---|---|
| `parse`（已有） | small / large / deep | 次/秒、MB/s |
| `to_sml` / `canonical_*` | 同上三组 | MB/s |
| `Value::get` | 深树 / 宽树 | 次/秒 |
| `dump` | 小/中/大文档（`CanonicalValue`） | MB/s、峰值堆 |
| `pack` | `pack_from_readers`（zstd 开/关） | MB/s |
| `load` | 全量解码 vs `Store::open` | MB/s |
| `get`（smlb） | `Store::get(path)` vs `MappedFile::get` | 次/秒、堆增量 |
| `Writer` | `add_segment_reader` | MB/s |
| `crypto` | 1 KiB / 64 KiB / 1 MiB 段解密 | MB/s |

### 5.4 三条已有判据，别当成「新发现」

| 判据 | 期望 | 出处 |
|---|---|---|
| mmap 打开 100 MB 只取一个字段 | **堆增 256 B** | `smlb/tests/mmap.rs`（计数分配器） |
| 200 KB 重复文本 pack | **705 B**（≈27×） | `examples/envelope.rs` |
| `Writer` 与 `dump` 产出 | **逐字节相同** | `smlb/tests/roundtrip.rs` |

### 5.5 组织建议

- 复用 `perf.rs` 的 `bench()` / `row()` / `count_allocs()`，**不要引 `criterion`**
  （仓库纪律：dev 依赖也锁小版本，且当前病根是「没有基线」不是「缺统计工具」）。
- 输出口径沿用 `docs/perf-baseline.md`：release、5 轮取最小、注明机器与 rustc 版本。
- **每项都同时报吞吐和峰值堆**：这个格式的核心卖点是内存，只报速度等于没测。
- 值层与容器层分开报，别合成一个总分 —— 那样出问题也定位不到。

## 6. 已知边界（别当 bug 修）

| 边界 | 说明 |
|---|---|
| `Writer` 不支持 `payloads[]` | 归档场景用 `pack_from_readers`；`Writer` 是「通用分段写」原语 |
| 加密件**不承诺字节确定** | `file_salt` 随机（D41：熵只进一次性标识） |
| 非 SHA-256 的流式写退化 | 增量实现只有 SHA-256；SM3 走「先读进内存」 |
| `verify` 通过 ≠ 可信 | 防伪造层 + 防换基文档；**防不了**「本来就是别人签的」 |
| 整条层链被剥离 | `verify` 看不出来（0 层也"通过"），必须 `--trust` |
| `caps.required` 不是权限系统 | 只是读侧拒绝，不阻止任何人读字节 |
| D13 `extract_text()` / D27 文本 feature / D28 64 B 量化 / D33 `DIR` 段 / S8 zeroize | **未做**，`docs/open-work.md` 有登记 |

## 7. 踩过的坑（省你几小时）

### 7.1 `smlkit-easy` 必须单独跑

`cargo test --workspace` 会报 `can't find crate for smlkit_easy`：
`swsml` 的 `[lib]` 同时是 `rlib`+`cdylib`、lib 名 `sml`，多个成员以不同 feature 集依赖它
⇒ 两次构建产物同名（cargo #6313）。CI 已拆成两步，见 `.github/workflows/ci.yml`。

### 7.2 构建目录会长到 50 GB

本次清理实测：**79,444 个文件 / 50.8 GiB**（用 \cargo clean\ 前后对比）。空间不足时 `link.exe` 报
`1318` / `1140`，看起来像代码错误，其实是磁盘满。

```bash
cargo clean          # 环境有批量删除守卫，直接 Remove-Item -Recurse 会被拒
```

### 7.3 fuzz 目录是独立 workspace

`rust/fuzz/Cargo.toml` 自带 `[workspace]`，**不要**把它加进根 workspace 的 members，
否则 `cargo test --workspace` 会尝试编译 nightly-only 的 crate。

### 7.4 改 `container.rs` 的偏移时先跑 `vectors --check`

21 例向量逐字节比对，是**唯一**能立刻抓到布局回归的闸门。

### 7.5 提交信息别写本机路径

`tools/check_private_assets.py` 会扫提交信息；写了 `D:\...` 会被判隐私泄露，
且**改写历史很麻烦**（本次因此合并重写了两条提交）。

## 8. 建议的下一步顺序

1. **先补 L1 的缺口**：把现有 `fuzz_targets/parse.rs` 扩成多入口
   （`parse_ordered` / `parse_with(collect_errors)` / `parse_file` / `tokenize`）。
   基础设施已经在了，这一步单价最低，而且 `parse_ordered` 是最近新增的路径、覆盖为零。
2. **再补 L2 / L3**：`smlb_load` → `smlb_get` → `value_canonical`。
   这三条构成「拿任意字节进来不许 panic / 不许 OOM / 能往返」的最小闭环。
3. **bench 拆三份**：`value.rs`（值层）先做——它是 `parse` 与 `smlb` 的公共底座，
   先把这层的数字拿到，后面两层的异常才能归因。
4. **再 bench `smlb.rs`**：dump / pack / load / get / Writer / 解密，
   每项同时报吞吐与峰值堆。
5. 之后才谈 T7：五端解码器可以只做 **JS + C**（覆盖浏览器与嵌入式），Lua / C++ 按需。
6. `smldb` 在 T7 之后再谈（它只是「可写数据库层」，不影响格式）。

> 排序理由：fuzz 的边际收益随「离输入解析起点越近」越大；bench 的边际收益随
> 「越靠公共底座」越大。两边都先做靠近入口/底座的那一层，剩下的才有归因能力。
