## 1. 逐条理由（供回查）

### D1 · 发布节奏

问题曾是「谁先发、什么条件发；`@version 50 "camelia" dev` 什么时候不再报 `E-FEATURE-004`」。
选项有三（先 `swsml` / 三个一起 / 先 `amberice` + `swml`），用户答「还没到发布」⇒ 三条都不取自今，
只做**准备**：`release.yml` 按依赖拓扑序写好但不执行；v5 表 A 回填照做，不动 `E-FEATURE-004` 的启用位。

为什么必须用户拍：发布不可逆，且 `swsml` 已发 18 版，0.7.0 的破坏性变更需要对外口径。

### D2 · 授权

用户原话「都 MulanPSL-2.0 了，基本算白送」⇒ 单授权保持。不新增 `MIT OR Apache-2.0` 双授权。

### D3 · 书名的承载位

用户反问「哪里用到它了，是不是已弃用」。核实：**没有弃用，仍是活的** ——
Rust `scan::resolve_edition`（与 `@version` 共用判据）、`js/sml.mjs` 的版本检测、
`grammar.sml` 的指令表、`js/probe-error-codes.mjs` 的版本矩阵用例。

结论：**不新增语法**。书名是普通数据（顶层 `title:` 键），CLI 推断规则（无 `title` 时取文件名）
写进规范即可；T13 由「语言扩展」降级为「文档补齐」。
理由：新增 `@title` 会造出两条表达同一件事的路径（谁优先？同时出现算什么？），
代价是五端解析 + 码表 + 文档，收益为零 —— 没有消费者需要把书名从数据里区分出来。

### D4 · 部署形态

原记录以为有 VPS。用户答：**一个定时请求 Cloudflare Worker，CF Worker 触发 GitHub Workflow
完成多平台的构建和发布**。故 `deploy.yml` 的 rsync / 健康检查 / 回滚那一套全部作废。

### D5 · 加密文件里的 `DIR` / `TYPED`

加密文件：除 `MANIFEST` 外每段必须 `enc != 0`，否则 `PlaintextSegmentInEncryptedFile`；
明文文件：出现 `enc != 0` 的段即 `EncryptedSegmentInPlainFile`。
`DIR` 已并入 seal / 加密流水线；加密文件里它是密文，`Store::get` 用不上索引（安全优先于速度）。

## 2. 通用原则（D3 的教训）

**先判断是「文档缺口」还是「语言缺口」。** 承载位已存在、只是没写进规范 ⇒ 补文档；
只有「表达不了」才考虑加语法。加语法要付出五端解析 + 码表 + 文档的代价，收益必须能说清。
