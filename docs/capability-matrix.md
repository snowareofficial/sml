## 0. 方法论与复现方式

### 0.1 铁律遵守
- 不重构、不优化、不改与本任务无关的任何实现代码。所有 `rust/ c/ cpp/ js/ lua/` 仅读不改。
- 判定一律**看输出文本，不看退出码**：Lua 与 C 在解析失败时进程返回码仍为 0，错误只写在 stderr/文本里（见 §5.2）。任一端若只看退出码，会得到「全绿」的假结论。
- 每一格都贴**实际跑出来的命令与输出**，不写「应该一致」。
- JS 的错误码在顶层 `r.code`（不是 `r.error.code`），已在探针中显式打印。

### 0.2 校准（必做，先确认每端「真的在看输入」）
用一份故意写坏的文档 `basic { a: 1`（未闭合块）喂给每端，必须报错；不报错 = 该端根本没解析，后面所有「ok」都不可信。

| 端 | 命令（节选） | 实际输出（节选） |
|----|----|----|
| Rust | `echo 'basic { a: 1' \| cargo run -q -p smltools -- --to sml 2>&1` | `smltools: parse error: sml: 未闭合的块/数组（遇到文件结尾，缺少结束符号 }） [E-PARSE-001]` |
| C | `echo 'basic { a: 1' \| .\_probe_c.exe` | `RESULT: ERROR` / `MSG: E-PARSE-001 未闭合的块（遇到文件结尾，缺少结束符号）` |
| C++ | `echo 'basic { a: 1' \| .\_probe_cpp.exe` | `RESULT: ERROR` / `MSG: E-PARSE-001 sml: 未闭合的块（遇到文件结尾，缺少结束符号 }）` |
| JS | `echo 'basic { a: 1' \| node _probe.mjs` | `RESULT: ERROR` / `CODE: E-PARSE-001` / `MSG: sml: 未闭合的块（遇到文件结尾，缺少结束符号 }）` |
| Lua | `echo 'basic { a: 1' \| luajit _probe.lua` | `RESULT: ERROR` / `MSG: E-PARSE-001 sml: 未闭合的块（遇到文件结尾，缺少结束符号 '}'）` |

五端全部报错 → 校准通过，后续证据有效。

### 0.3 各端统一入口（复现用）
- **Rust**：`cd rust && echo '<sml>' | cargo run -q -j 1 -p smltools -- --to sml 2>&1`（错误走 stderr，退出码 1）。
- **C**：`gcc c/sml.c _probe_c.c -o _probe_c.exe -Ic` 后 `echo '<sml>' | .\_probe_c.exe`（入口 `sml_parse`；`file` 模式走 `sml_parse_file` 以展开 include）。
- **C++**：`g++ -std=c++17 cpp/sml.cpp _probe_cpp.cpp -o _probe_cpp.exe -Icpp`（需 `PATH` 含 `C:\msys64\ucrt64\bin`）后 `echo '<sml>' | .\_probe_cpp.exe`（入口 `Parser::parse`）。
- **JS**：`echo '<sml>' | node _probe.mjs`（`node` = `<node-dir>\node.exe`，入口 `parseSafe`）。
- **Lua**：`echo '<sml>' | C:\msys64\ucrt64\bin\luajit.EXE _probe.lua`（入口 `Sml.load`；`file` 模式以文件所在目录为 include 沙箱）。

> 备注：`c/build_check.py` 在 `fix/derive-int-overflow` 基底里**不存在**（仅落在 `main` 的 `a1d0786`，非本分支祖先）。因此「开工前检查」中的该步按脚本无法执行；C 端改用直接编译 `c/sml.c` 验证（即上文 C 入口），行为等价。其余三项（check_private_assets / lua/run_check.py / cpp/build_verify.py 五个原生 target）均通过；cpp 的 RS-BRIDGE 因 worktree 未构建 Rust cdylib 而跳过（属已知不可跑项，非本任务范围）。

## 2. 逐格实证（实际命令 + 输出）

### 2.1 格子1 — include "path"
测试文件：`_inc/main.sml` = `include "sub.sml"\nroot: 1\n`，`_inc/sub.sml` = `sub: 2`。

- **Rust**（文件模式）：`cargo run -q -p smltools -- -i ../_inc/main.sml --to sml`
  ```
  root: 1
  sub: 2
  ```
- **C**（file 模式）：`_probe_c.exe file _inc/main.sml`
  ```
  RESULT: OK
  DUMP:
  sub: 2
  root: 1
  ```
- **C++**：`_probe_cpp.exe file _inc/main.sml`
  ```
  RESULT: OK
  DUMP:
  include: sub.sml
  root: 1
  ```
  → C++ **未实现** include：把 `include "sub.sml"` 当成普通键值 `include: sub.sml` 静默吃下（无错误、未展开）。
- **JS**（虚拟文件表 `_probe_inc.mjs`）：`node _probe_inc.mjs`
  ```
  RESULT: OK
  VALUE: {"sub":2,"root":1}
  ```
- **Lua**（file 模式）：`luajit _probe.lua file _inc/main.sml`
  ```
  RESULT: OK
  DUMP:
  sub: 2
  root: 1
  ```

### 2.2 格子2 — 转义集
策略校验：先喂未知转义 `\q`，五端**全部**返回 `E-LEX-004` → 说明「已知转义返回 OK」是**真支持**而非「静默保留字面量」（否则 `\q` 也会 OK）。

- 未知转义 `k: "\q"` 五端均：`E-LEX-004 字符串含未知转义符 \q（仅支持 \n \t \r \0 \" \\ \uXXXX）`（Rust/C/C++/Lua）/ `CODE: E-LEX-004`（JS）。
- 基础转义 `\0 \n \t \r \" \\`：五端对 `k: "a<esc>b"` 全部 `RESULT: OK`（Rust/C/Lua 经 `--to sml`/`sml_dump` 还原；JS `VALUE` 显示 `a\u0000b`、`a\nb` 等；C++ dump 还原）。
- `\uXXXX`（固定四位，`\u0041` → 期望 `A`）：
  - Rust：`k: aAb` ✅
  - C：`k: aAb` ✅
  - Lua：`k: aAb` ✅
  - **C++**：`RESULT: ERROR` / `MSG: E-LEX-005 sml: unicode 转义位数不足（须四位十六进制或 \u{...}）` → 只认 brace 形式 `\u{41}`（复测 `\u{41}` → `k: aAb` ✅）。
  - **JS**：`VALUE: {"k":"aA1b"}` ⚠️ **解码错误**——正确应为 `aAb`，实际多了末位十六进制数字 `1`。源码定位 `js/sml.mjs:131` 应为 `i += 5` 却写成 `i += 4`（少跳过 `u` 自身），导致末位 hex digit 被当普通字符拼回字符串。
- `\a \b \f \v \'`：五端**全部** `E-LEX-004`（Lua 文案明确「仅支持 \n \t \r \0 \" \\ \uXXXX」，见 `lua/lib/sml.soup:187`）。**TODO「Lua 额外支持」在本分支为假**。

### 2.4 格子4 — $env.VAR 内联
设环境变量 `MY_TOKEN=secret123`（未定义场景则清空该变量）。

- 裸词 `k: $env.MY_TOKEN`：五端均 `secret123` ✅。
- 引号整串 `k: "$env.MY_TOKEN"`：
  - Rust `k: secret123` ✅ / C++ `k: secret123` ✅ / JS `{"k":"secret123"}` ✅ / Lua `k: secret123` ✅
  - **C**：`k: $env.MY_TOKEN` ❌（引号内不替换，原样保留——C 只在裸词做 `$env`）。
- 引号内嵌入 `k: "pre-$env.MY_TOKEN-post"`（`MY_TOKEN=abc`）：
  - **Rust**：`k: pre-abc-post` ✅（真正的字符串内插值）
  - **C/C++/JS/Lua**：`k: pre-$env.MY_TOKEN-post` ❌（原样保留；其 `$env` 匹配是「整串锚定」的，仅当整个引号内容恰为 `$env.X` 才替换，见 `js/sml.mjs` 的 `/^\$env\.(.+)$/` 锚定）。
- 未定义变量 `k: $env.MY_TOKEN`：五端均 `k: ""`（静默当空串，不报错）。

### 2.5 格子5 — 错误信息与失败行为
多个失败场景实跑，错误**码**五端完全一致：

|---|---|
| `basic { a: 1`（未闭合块） | `E-PARSE-001` |

| `X { a: B::C }`（裸冒号） | `E-PARSE-006` |

## 3. 「我原本以为一致、实测不一致」清单（本任务最值钱的产出）

1. **TODO 称「Lua 额外支持 \a \b \f \v \'」—— 实测五端全部拒绝这组转义（E-LEX-004）。**
   Lua 源码 `lua/lib/sml.soup:187` 注释明确收窄到 `\n \t \r \0 \" \\ \uXXXX`。所谓「Lua 额外」在本分支是**假预期**。→ 属「文档/预期错误」，需修订 TODO/IDEAS，而非改实现。

2. **JS 的 `\uXXXX`（固定四位）解码错误**：`\u0041`、`\u0065` 分别得出 `aA1b`、`ae5b`（正确应 `aAb`、`aeb`）。根因 `js/sml.mjs:131` 的 `i += 4` 应为 `i += 5`。→ 这是**实现 bug**，JS 端 `\u` 固定形式不可用；brace 形式 `\u{...}` 未验证但受影响逻辑不同。

3. **C++ 不支持 include 指令**：把 `include "sub.sml"` 静默当键值 `include: sub.sml`，不报错也不展开。Rust/C/JS/Lua 均正确展开。→ C++ 缺失该功能（或静默降级），属「未实现 + 静默处理」双重问题。

4. **大整数（>2^53）跨端行为分裂**：Rust/C/C++ 精确保留为整数；**JS 升为字符串**（保真但类型改变）；**Lua 转成 float 并丢精度**（`3.3010620150307e+17` ≠ 原值）。→ Lua 此处会静默破坏数据，最危险。

5. **`1.0` 与 `1` 的区分**：**Rust 保留 `1.0` 为浮点**（`n: 1.0`），C/C++/JS/Lua 全部归一为 `1`（整数）。→ 若依赖「尾随 .0 表示浮点」的语义，只有 Rust 满足；其余四端无法区分（与 `js/sml.mjs` A1 注释「无法区分 1.0 与 1」一致）。

6. **`$env` 在引号内的差异**：
   - C：引号内根本不替换（裸词才替换）。
   - C++/JS/Lua：引号内仅当**整串**恰为 `$env.X` 时替换，嵌入场景（`pre-$env.X-post`）不替换（锚定匹配）。
   - 只有 **Rust** 做真正的字符串内插值。
   → 裸词形式五端一致；引号形式三档行为。

7. **C++ 浮点打印丑**：`3.14` 输出 `3.1400000000000001`（naive `setprecision(17)`），其余四端用最短表示（`3.14`）。纯渲染差异，不影响数值。

8. **科学计数法渲染差异**：输入 `1e10`，Rust 输出 `1e10`、C 输出 `1e+10`，C++/JS/Lua 展开为 `10000000000`。识别一致，仅展示形式不同。

9. **「TODO 称 JS/C 对 `X { a: B::C }` 静默 ok、制造数据污染」—— 实测本分支五端全部返回 `E-PARSE-006`。**
   即该分歧**已被修复/对齐**（W10 错误码工作 + 后续修复的成效）。→ 这是「我以为不一致、实测已一致」的反向发现，同样重要：TODO 该条已过时，可据实更新。

## 4. 对 Q1 / Q2 / Q3 的答复

**Q1 行列排布**：采用「行 = 特性子项，列 = 五端」的矩阵（见 §1），每格标注 ✅/⚠️/❌ 并在 §2 贴实跑命令与输出。文档正文即证据，不另起表格孤岛。

**Q2 不一致标注档位**：用三档——「⚠️ 差异（行为/输出可观察不同）」「❌ 未实现」「⚠️ 静默处理（错当别物/丢数据/不报错）」。
关于第四档「已知不接受此差异」：**不需要单独设档**。理由：五端错误**码**已对齐（W10 成果），仅**文案**不同——而按 I-9 决策 C，「运行时段只加中文、英文静态目录不碰」，文案差异属已知可接受。真正需要修的是「行为」层面的差异（静默/未实现/丢精度），已归入 ❌/⚠️ 静默处理。因此第四档并入「⚠️ 差异（已知可接受：仅文案）」与「需修的差异」两类即可，避免无谓分档。

**Q3 跑不到的格子**：一律**留空 + 写明原因，绝不推断**。本调查所有格子均成功触发；唯一需注意的边界是 C 的 include——其内存模式 `sml_parse` 不展开 include，须用 `sml_parse_file`（file 模式）才展开，§2.1 已用 file 模式覆盖，故不留空。若未来某端某特性确无法触发（如构建不出），将明确标注原因而非猜测。
