## 12. `.ambr` 用途定位与生态对标【草案 · 待拍板 · 未定 · ⚠️需二次蒸馏】

> 本节只是技术分析 + 取舍，**尚未拍板**，新功能仍暂缓、暂不实现。
> ⚠️ **二次蒸馏**：以下是未经整理的原始信息，需在拍板前把它精炼成「取舍明确 + 结论唯一」的定稿，避免携带冗余分析。
> 记下供决策与后人参照：📌 `.ambr` 不是通用互换格式，是 sml 专属的「持久化 / 传输 / 惰性读取」信封。

### 12.1 用途定位 —— 先构思"为什么需要它"

二进制**不是必须**。它本质是：**把 protobuf 场景的优化（体积 / lazy / 随机访问）做成 sml 文档原生的、无需 schema、无需 codegen 的一层**，可叠加 zstd 帧（必要时）。

只有命中下列场景才有价值；纯「解析→用→丢」的调用方完全用不到它：

| 场景 | 用到的机制 | 数据支撑（`spec/format.md §3`/`spec/smldb.md §5`） |
|---|---|---|
| a. 文档反复存/读（DB / 文件） | BLOB 存原始字节 + mmap | DB 0.18×、单文档读 0.003 ms |
| b. 大文档随机访问 / 惰性（选择器、按需读子树） | 前序 + `subtree_sz` + 绝对偏移 | O(1) 跳整棵，不整树解码 |
| c. 内存受限（嵌入式 / 服务端常驻） | Node 36 B 平坦布局 + Span 共享 | A→B 降 75%，2.6 MB RSS |
| d. 批量传输 / 网络 | zstd -3 帧 | 0.107×（低于 protobuf+zstd） |
| e. 跨平台分发 | 明码 LE + u32 偏移 + 零依赖 | 可 mmap / WASM，无 arch 依赖 |

**它不是答案的场景**（职责划分）：
- 要跨语言 schema 契约、字段号演进约束 → **protobuf**
- 人类可读写的互操作 / 手改 / diff → **文本 sml / toml / json**
- 纯 parse-and-drop → 全部不需要，.ambr 可整体搁置

### 12.2 与 toml / json / protobuf 库的全面对比（Rust 生态）

| 维度 | sml 文本 | `.ambr` | toml (`toml_edit`) | json (`serde_json`) | protobuf (`prost`) |
|---|---|---|---|---|---|
| 人类可读写 | ✅ 易 | ❌ 字节 | ✅ 易 | ✅ 易 | ❌ |
| Schema 要求 | 无 | 无（固有多叉树节点模型） | 无 | 无 | **必须 `.proto` + 代码生成** |
| 类型保真 | Int/Float(+raw)/Bool/Str/Array/Object/null | 同左 | 弱（日期无、数字弱） | 弱（f64 混用） | 强但受 schema 约束 |
| 体积（相对原文 1.0） | 1.000 | 裸 0.172 / zstd 0.107 | ~≈ json | 文本级大 | 0.659 |
| 随机访问 | ❌ | ✅ O(1) 跳子树 | ❌ | ❌ | ❌ 须整树解码 |
| 惰性/按需 | ❌ | ✅ 绝对偏移 | ❌ | ❌ | ❌ |
| mmap | ❌ | ✅（源由 OS 分页） | ❌ | ❌ | ❌ |
| 解析后内存 | 高（String 空气税） | 低（Node 36 B） | 高 | 高 | **仍 String/Vec，零收益**（§11 误区） |
| 选择器/子树查询 | ✅ sml 原生 | ✅ | ❌ | ❌ | ❌ |
| 全文检索 | 经 extract_text→FTS5 | 同左 | SQL LIKE（慢） | 不确定索引 | ❌ |
| 核心零依赖 | ✅ | ✅ | ✅ 纯 rust | ✅ 纯 rust | ❌ prost+codegen |
| 格式演进/向前兼容 | 文本 diff 易 | version + 容忍未知 tag | 文本 break | 文本 break | 靠字段号，最优 |
| 跨语言互换性 | ✅ 文本皆可 | 需专用库读 | ✅ | ✅ | ✅ 最优 |

**结论倾向**：三者职责不打架 —— schema 契约互交换 protobuf；人类互操作走文本 sml/toml/json；**sml 文档的持久化 + 随机访问 + 零依赖内存走 `.ambr`**。

### 12.3 `.ambr` 格式的语法取舍（设计决策面，各带取舍理由）

| 决策 | 取舍 | 理由 / 代价 |
|---|---|---|
| magic `"AMBR"` + version + flags(明码 LE) | 固定 LE 牺牲 BE 直接读 | 换跨平台确定性（同 protobuf）；version 留演进闸门 |
| 计数用 varint | 小文件省字节，解码有分支 | count/ids 小值占多数；体积 vs 解码速度 |
| 全局 strtab 去重 | 淘汰训练字典（`spec/format.md §3` 534 vs 540 无收益） | 代价：写入需 hash 去重，`u32` 偏移 ≤4 GB；超大文档要 u64 |
| 前序 + `subtree_sz` | O(1) 整棵跳过 ↔ 插入/修改要重算 | 与 `spec/smldb.md §5.9`「Rewrite 全量重写」互补，非 append 友好 |
| 不内带自定界（无长度帧头） | 格式职责单纯 | 文档边界靠容器告知（单文件 / DB BLOB 长度 / zstd 帧） |
| 键序决定性（按键排序写） | 换来确定性字节 + 缓存 / diff / 去重 | 代价≈0（BTreeMap 本就按键序） |
| Float 保留 raw（`has_raw` flag） | 保 P3 原文逐字还原 | 占 1 flag 位 |
| 未知 tag 容忍 | 靠 `subtree_sz` 跳过未知子树 | 向前兼容；约束：新 tag 必须在结构上可整体跳过 |
| 标签 interning 分两层 | 内存=封闭词表 `Tag` enum；`.ambr`=strtab 偏移 | 职责不混，内存与序列化各做各的 |

### 12.4 建议（技术意见，**未拍板**）

- 📌 认同你的判断：**`.ambr` 不是必须**，定位 = sml 文档的持久化/传输/惰性信封，恰好覆盖「protobuf 场景优化 + 必要时 zstd」。
- 若目标是纯解析库 → `.ambr` 整块可搁置，proto 优化对纯解析用户零收益。
- 若目标是文档库（存 / 查 / FTS，`spec/format.md §1` 架构里的 `smldb` BLOB 层）→ `.ambr` 是前提，值得做。
- **触发条件**（仿 `spec/smldb.md §6.6`，命中再动手）：出现持久化/重复读需求、内存受限目标、或批量传输；否则暂停。
- 明确不做：不把它做成通用 schema 互换格式（那是 protobuf 的地盘），不自造通用 value 二进制（serde_json/bincode 可代）。

## 15. 对象键序（key order）问题【记录 · ⚠️须先确认为哪个点】

> 用户点名「记一下键序的问题」。落档现状约定 + 候选分歧点，**未拍板**。
> ⚠️ 先对齐：下面区分「已是约定」与「可能要讨论的点」，需用户确认到底记哪一面。

### 15.1 现状约定（已写进文档，是**既定事实**，非待定）

- Rust 侧 `Value::Object` 用 `BTreeMap` ⇒ 序列化**按键字典序**输出（`rust/README.md` / `sml-value/README.md`）。
- C / C++ / JS / Lua **保书写顺序**。
- 语言约定：**对象键序不保证**；需要有序序列时用**数组** `[ … ]`（`site/…/book/ch12-smltools.md`、主 `README.md`）。
- 五端一致性中，键序（C 保源序 vs Rust 排序）被归为「纯渲染差异」，**不误报**（`tests/conformance/known_divergences.md:27`）。
- `smltools` JSON 互转侧：JSON 键按字典序输出，原始书写序不保留（`ch12-smltools.md:93-95`）。

### 15.2 候选分歧点 / 可能要想的问题（逐个待确认）

1. **跨五端字典序 vs 源序不一致**：同输入五种实现产出字节不同 —— 是否要统一？
   （现有裁决：视作语言约定、接受分歧，`known_divergences` 已登记）
2. **确定性问题**：`smltools` 推断（infer）走 `BTreeMap` 保证同输入逐字节相同（`TASK-agent-w24.md:391`）——
   这是「效果好」的一方；会不会有人要求 Rust 也保源序来做 diff / 人类可读往返？
3. **与 §12.3 `.ambr`「键序决定性（按键排序写）」的关联**：二进制格式已拟按排序写，换取确定性字节 ——
   与当前「对象键序不保证」是否要统一成一个总说法？
4. **`to_string_direct`（I-1 直出）特意保留字段声明顺序**（为保 `BTreeMap` 重排的替代）——与「对象键序不保证」
   是否存在文档/心智上的冲突需要澄清？

### 15.3 「少量空间换保序」的方案分析（用户询问，未实现）

用户提：「能不能拿少量空间换（单独做一个树状表）解决键序保序？或更好的方案？」

**现状关键**：`Value::Object` = `BTreeMap`（dict序），`as_object` 暴露 `&BTreeMap`，
dump 直接遍历它输出；但 `ser_text.rs` 已另走一条 `Vec<(String, Node)>` **保序**路子（直出用，不进 `Value`）。

**对「单独树状表」的判断 —— 方向对了一半，形态不对**：
- 需要额外信息保住序 ✓（直觉正确）
- 但旁路顺序表（无论 `Vec<String>` 还是树）**要再存一份 key** ⇒ String key 空气税 ×2（`spec/format.md §2`：一份≈48B）。
  对象越大这个「换」越贵，不是真正「少量空间」。
- 还要同步两份结构（插/删/改 key），不一致就静默乱序，心智负担比 dict序 更糟。

**更好的方案（三档）**：
| 方案 | 结构 | 序 | 查找 | 空间 | 复制度 |
|---|---|---|---|---|---|
| B1 | `Vec<(String, Value)>` | 保序天然 | O(n) 线性 | key 一份，比 BTreeMap 省（无二叉树指针） | 低；`ser_text` 已趟过 |
| B2 | Vec 保序 + `HashMap<String,usize>` 索引（本地 IndexMap） | 保序 | O(1) | +~8B/键 索引（key 仍一份） | 高；零依赖铁律禁引 indexmap，须自实现≈200 行 |
| B3 | 不动结构，dump 按源序排 | 需另记源序 | — | 等同一份序信息 | 等于没解法 |

**技术意见（非拍板）**：放弃「树状表」。偏爱 **B1** —— 贴 sml 实际形态（小对象、配置文件式）、
key 更少一份、零依赖，`ser_text` 已趟过路；O(n) 对真实负载够用。需要大对象随机查时再给 B1 补 B2 索引，
往后升级不推倒。B2 仅在「大对象 + 频繁随机查」才值得。

**⚠️ 大副作用（须先裁决）**：改保序会**推翻已写死多年、且五端一致性登记为「不误报差异」的语言约定**
（README 明文「对象键序不保证、要保序用数组」）。动手前须重新对齐 `known_divergences` + conformance，
并裁决「是否为保序而付出这份破坏性代价」。

> 📌 现状：未实现、未拍板。默认仍是「对象键序不保证」。方案需用户裁决后再谈落地。

### 15.4 「树的局部保序」可行性（用户认可方向，未实现）

用户问「树的局部保序可以支持吗」，方向获得认可（`ok`），落档分析如下。

**三种含义的界定**：
- **A. 个别对象 opt-in 保序**（新变体 `OrderedObject(Vec<...>)`）—— 可行、破坏面最小。
- **B. 按语义分层保序**（配置子对象保序 / 多实例聚合块 dict 序）—— 语义最贴需求，
  但 parser 在归并时刻往往还不知道块的性质（类型到解析末尾才定型），实现难度高。
- **C. 只对根到某深度路径保序** —— 动机弱、实现最拧巴，不推荐。

**红线圈定（A 能成立的前提）**：保序只对**未参与合并**的干净子块成立。sml 的归并路径
（`&base` `extend`、emit 片段 `extend`、子容器 `insert_field_val`）语义本质是「按名并集」，
一进 `extend`，源的书写序在数学上就丢了 —— 合并过的对象给「保序」是**假保序**（给出拼装后顺序，更误导）。

**落地方向（非拍板、未实现）**：
- 走 **＋A 型**：`Value` 加新变体，不动 `Object(BTreeMap)` 的 log n 查找与既有破坏面；
  边界绑定「该对象未参与合并」。
- 与五端一致性天然兼容：只有 Rust 侧显式新变体保序，老路径行为不变，`known_divergences` 不动。
- 对比 §15.3：全树保序是大手术，局部 opt-in 是小补丁，代价与收益都小一个量级。

| **D17** | **系统时间不可信**（可被改 / 可能离线 / 连不上权威服务器） | 有效期只是**提示**，不进验证的必要条件 |
| **D18** | **基座定位**：只做「SML 数据的二进制化」；信任根选择、撤销、锚点验证交给调用者 | 与 D14 同向：策略不进格式 |
| **D19** | **追加默认链式**；多来源须先合并成一个文件对象再按序追加（线性，无分支） | 文件内永远一条历史 |
| **D20** | **并发写 = 多读一写**（写者加锁；读者 mmap 旧版本不受影响） | 追加必须基于「当前头」，`prev_hash` 不匹配即冲突 |
| **D21** | **多读多写交给 `smldb`**（SQLite WAL），`.ambr` 不自建 OCC | 与 D4「两档不混」一致 |
| **D22** | **数组补丁 = 整体替换**（不拼接、不按 index 合并） | 按位改数组是 featag `[n]` 的职责，避免两套机制打架 |
| **D23** | **`.ambr` 可以装「不经过 SML 的东西」**：外来载荷（其它格式的原始字节）是**一等段**，原样存取，库不解码 | ⇒ `.ambr` = **容器（manifest + 段）+ Value 编码**，不是「只能装 Value」的格式；与 D12「其它格式嵌入」、D14「不做媒体编解码（只当信封）」一致 |

| **D26** | **API 面 = 5 组 20 个函数**（值↔字节 / 文件 / 读 / 写 / 流·能力·安全），可作为其它 crate 的**样板** | 组内一名一职；`append` 是唯一写路径；不给 `save` / `update` / `set` / `sync` |
| **D27** | **逆向导出走 A + C 兜底**：默认 `to_value()` + 由 `smltools`/`swsml` 出文本；`amberice` 另提供可选 feature `text` 转发到 `sml::emit::to_sml` | 不内置第二个文本发射器（B 方案）—— 那是长期债 |

### 16.3 待裁：脱敏与串口采集场景（2026-11-09 登记）

> **待裁决**：以下是场景边界分析，**不是结论**。`docs/amberice/` 没有「脱敏 / 串口」的定义。
> 两个问题都指向同一条约束：**写侧只能追加或整体重写，不能只动部分字节**。

**问题**：一份已写出的 `.ambr` 能否事后只把敏感字段抹掉；`.ambr` 能否直接承接串口软件的
逐帧采集。

#### 脱敏：只能在写入前做

| 做法 | 判定 | 依据 |
|---|---|---|
| 写入前把敏感值换成占位 / 哈希，再 `dump` / `append` | 可行 | 值层处理，与容器无关 |
| 追加 `patch` 层把敏感键覆盖成遮盖值 | **不可当脱敏** | 旧字节原封不动；`history --at N` 可回放旧值，`cat` / `ls` / `unpack` 可读；段摘要与层链恰好证明旧字节未被改（`spec/format.md §21.1b`） |
| 重新 `dump` 一份，或 `compact` 后销毁全部旧件 | 唯一抹除路径 | 不变量 3 的例外只有 `compact`，且必须重签、旧 `--trust` 锚点作废（`§23.1`、`§21.1b`） |
| 段级选择性加密 | 粒度是段，不是字段 | `crypto_plain` 白名单（`rust/amberice/src/container.rs`）；`MANIFEST` 永不加密（`§19.13.2`），段头与 `payloads[]` 的 name / len 是明文；`Store::open` 对加密文件直接拒绝零拷贝读取（`§19.13`、`§25.6`） |

介质层抹除不在格式职责内：S8 的 `zeroize` / `mlock` / `MADV_DONTDUMP` 是 `§24.1` 清单里的
**可选**对策，代码未实现（`rust/amberice/src/sha256.rs` 注明「没有清零」）；mmap 页换出、
文件系统与 SSD 磨损均衡同样不受格式控制。`§24.4 ⑤` 的溯源指纹用于泄露追踪，不是脱敏。

#### 串口采集：归档可，实时逐帧不可

| 约束 | 出处 |
|---|---|
| 「实时读写」不塞进 `.ambr`；不承担可变 DB 文件（MVCC）与追加式日志 | D4 / D14 |
| 多读多写交 `smldb`（`draft`，未开工） | D21 |
| 规模信封：写入 ≤ 1/s、每批 fsync | `§10` |
| 按帧追加暴露「改了哪些键、多久一次、改多大」；建议批量提交 + 固定大小的层 | `§24.1 S4` |

可用面：`TYPED` 强类型载荷 + 外置 schema（`§25`）适合固定帧结构；`subtree_len` 跳兄弟 +
mmap（`§19.10`）与 `FrameCursor` 按需解帧（`§19.12`）适合事后抽查与回放；冷数据裸 `.ambr`
+ mmap、导出走 zstd（`§4`），保密场景按 S2 用 `--no-compress` 断开压缩与长度的关联。
端口侧以 `ref/ports.md` 为准（该文正文为唯一事实来源；本节写作时的端口欠账此后已清）。

#### 待裁三问

1. 脱敏是否定为「写入前的调用方责任」，格式明确不提供事后局部抹除？若要事后抹除，
   需引入「可覆写段 + 独立校验域」，即改不变量 3，并回答旧签名与 `--trust` 锚点怎么办。
2. 高频采集是否正式划归 `smldb` / 外部日志，`.ambr` 只收批量归档？若另立写入路径，
   `§10` 规模信封与 D14 的排除项要一起重裁。
3. 是否为串口上位机补 C# FFI（`ref/ports.md` 的剩余三端配方）？

> **已定（2026-11-10，D53）**：三问按「写前脱敏 / 批量归档 / FFI 单列」收口。本节保留为场景分析，
> 不再待裁；脱敏与高频的落地形状见 D53，`SOURCE` 另由 D46 收口。

#### 16.5.1 形态决定论：先选写入形态，再谈需求

| 形态 | 典型场景 | 非整文件 | `compact` | 签名 |
|---|---|---|---|---|
| **A 长寿命可变文件** | 审计日志、长期累积、签名后追加 | 必需 | 必需 | 视信任边界 |
| **B 一次成型文件** | 会话 / 批次 / 快照即一个文件（串口一次采集、导出） | 不需要（写完不再改） | 不需要（恒 1 层） | 不需要（除非外发） |
| **C 多写多查** | 文档库、按条件筛 | 不归 `.ambr`（D21 → `smldb`） | 不归 | 不归 |

判据：**「同一份文件是否被反复修改」比「写入多快」更能决定要不要追加能力**。选 B 形态时，
追加、`compact`、签名三项需求一起消失。

#### 16.5.2 写路径现状（代码事实）

| 事实 | 位置 |
|---|---|
| `append_layer` 把旧文件整体复制进新 `Vec<u8>` 再返回 | `rust/amberice/src/sign.rs`（`out.extend_from_slice(bytes)`） |
| CLI `append` 默认覆盖原文件，但落盘走 `write_atomic`：tmp + `rename`，不截断正式文件；该路径不做 `fsync` | `rust/amberice/src/main.rs`（`write_atomic`） |
| `check` 回扫最多 1 MiB 找完整 Trailer，其后多出的字节按「半截追加或尾垃圾」报出；`info` / `open_raw` 仍只校验段边界 | `rust/amberice/src/container.rs`（`check` 第 6 步）、`rust/amberice/src/layer.rs`（`find_trailer`） |
| `Trailer::parse` 只看 EOF 前 64 B | `rust/amberice/src/layer.rs`（`TRAILER_LEN`） |
| 读当前值按序合并全部层 | `rust/amberice/src/store.rs`（`value` → `apply_patches`） |

由上推出的结论：追加成本仍是 **O(文件大小)** 而不是 O(补丁)；崩溃不再毁掉原文件，
但「整文件复制」的内存与耗时代价没变。尾垃圾检测只覆盖「完整 Trailer 之后多字节」；
截尾行为已由探针 2 实测并补上 `check` 告警（§16.5.8）：读端仍退回基文档，但 `check` 判未通过。

#### 16.5.3 「非整文件」两种含义，只做第一种

| 含义 | 做法 | 判定 |
|---|---|---|
| **尾部追加** | `seek(End)` 只写层记录 + 新 Trailer；不复制、不截断 | **技术意见：做**。同时解决崩溃安全与大文件追加成本 |
| **就地覆写** | 改中间已有字节（原地改某个值） | **不做**。破不变量 3、段摘要全废、`len` 固定、旧签名与 `--trust` 锚点作废 |

尾部追加必须同时定义**尾部恢复**：`Ingestor::recover` 可截掉崩溃留下的半截记录，`check`
借 `find_trailer` 报出完整 Trailer 之后的尾垃圾（回归用例 `tests/unsigned.rs`）。
`Trailer::parse` 仍只认 EOF 前 64 B。探针 2 已实测（§16.5.8）：截尾 1 / 32 / 64 / 128 B
时 `layers()` 一律返回空链、读端静默退回基文档，`CountMismatch` 四档均未命中；
`check` 已补一档告警（无完整 Trailer 但段区之后有字节 ⇒ 判未通过）。
**不得按「能优雅退化」写进规范**；尾部恢复本身仍待设计。

#### 16.5.4 归档与盖章：拆成四件事，各有判据

| 机制 | 该不该做 | 判据 |
|---|---|---|
| 段摘要（不签名） | **保留，别省** | 挡意外损坏（磁盘 / 传输 / 截断），成本近零 |
| 签名（盖章） | **按信任边界触发，默认不做** | 只有「验签的人是别人」才值：外发交付 / 取证 / 审计 / OTA 包 |
| `compact`（压层） | **维护操作，非产品功能** | 层只增不减、`value()` 逐层合并；阈值待探针 3 |
| `pack`（多件一包） | **按需，仅分发 / 传输** | 单文件日用软件不需要；**禁止**当归档目录库（索引需求 → `smldb`） |

口径：**摘要挡意外损坏，签名挡蓄意伪造**（`spec/format.md §3.7`），两者不能互相替代，
也不该混称「更安全」。

#### 16.5.5 高频暂存：不新开格式

技术意见（未拍板）：高频暂存的缺口在**写路径**，不在字节布局；换成任何新格式，只要写路径
仍是整文件重写，问题原样复现。

- 暂存层若要做，形态是**提交协议**而不是格式：定长头 + 载荷（`canonical_bytes` 或不透明字节）
  + 摘要 + 尾标记，双槽轮换，读端取 `seq` 最大且校验通过者。不需要层链、`compact`、
  版本迁移、五端解码。
- 依赖方向：`暂存层 → amberice`（只借 `dump` / 散列 / 可选 AEAD），**不共享容器**。因此
  `sha256.rs` / `hash.rs` 是否下沉出 `amberice` 需一并裁决，否则是「为一条校验和拖进整个信封 crate」。
- 升格判据（命中任一才谈「格式」）：出现第二个读 / 写端；数据必须活过版本升级；需要跨语言实现。
- 三条都不命中时，正确做法是**调用方私有编码**（`canonical_bytes` 或文本）+ 原子替换，不进 `amberice`。

#### 16.5.6 日用软件（串口监视器）落地形状

| 环节 | 结论 |
|---|---|
| 实时收帧 / 显示 | 用应用自己的环形缓冲；`Store` 是只读导航，不是可写内存模型 |
| 落盘 | 按时间或大小**分卷**（一次会话若干 `.ambr`），不要一个文件写一整天 |
| 帧数据 | 原始字节进 `EMBED`（D23），坏帧 / 截断帧照样存；**建议聚块**，不按帧一条 `payload` |
| 元数据 / 固定帧结构 | `VALUE` 存会话元数据，`TYPED` + `SCHEMA` 存结构化帧（D45） |
| 事后回放 | mmap + `subtree_len` 跳兄弟 + `FrameCursor` 按需解帧 |
| 分发 / 上报 | 段级 zstd；保密场景按 S2 用 `--no-compress` |

工程面现状（非格式问题）：`amberice` / `amberice-ffi` 均 `publish = false`，外部软件只能
path 依赖或内嵌；多端 FFI 已全端通过（含 C# / Go / Ruby，见 `ref/ports.md`），串口上位机的
语言面不再是阻塞项；`errors/codes.sml` 无 `AMBR` 码，错误以 `AMBR: …` 文本透传，界面要自己映射。

#### 16.5.7 口径修正（讨论中出现过、需更正的表述）

| 项 | 更正 |
|---|---|
| **C# / Go / Ruby 三端 FFI 未做** | **错**。三端 2026-11-10 已实测通过（22/22 逐字符 + 往返，`ref/ports.md`）；多端状态以 `ref/ports.md` 正文为准 |
| 每条 `payload` 开销「约 40 B」 | 实际约 **100 B 量级**：摘要按 64 字符十六进制串写进 manifest，再加 `name` / `len` / 对象键 |
| 「8 MB 重写照百毫秒」 | 更差也更没把握：实测点只有 4 MB = 1.84 ms、16 MB = 121.79 ms（`spec/smldb.md §5.5`）；本机 .NET 微基准 8 MB ≈ 1.5–2.0 s，但本机**不是标准测试环境**、波动大，只作量级参考、不可当基线（见 `ref/claims-audit.md §7`） |
| 把「写入 ≤ 1/s」当代码上限 | 那是 §10 的**规模信封裁决**，代码没有任何限流 |
| 「半截尾能优雅退化」 | **已实测并否决**（探针 2，§16.5.8）：截尾 1/32/64/128 B 一律 `layers()` 空链、读端退回基文档，`CountMismatch` 四档均未命中；不是优雅退化，是静默丢一次写入。`check` 已补告警判未通过，读端行为未改 |
| 「签名不提供更多安全」 | 措辞过头：签名挡蓄意伪造，摘要挡不了；默认不签的理由是「没有第二方验签」，不是签名无用 |
| 「散列与加密都是零依赖自实现」 | 只有 SHA-256 / SM3 / BLAKE3 是自实现；加密依赖 `aes-gcm` / `hkdf` / `sha2` / `argon2`（`crypto` feature） |

#### 16.5.8 探针实测（2026-11-10，release / Windows x86_64）

三条探针均已跑完，可复现探针已入库：
`cargo run --release -p amberice --example probe_layers`（`rust/amberice/examples/probe_layers.rs`）。
数字为多轮最小值，口径与 `swsml/ref/perf-baseline.md` 一致；**只作裁决依据，不进性能基线**。

1. **成本**：8 MB / 64 MB 的 `.ambr`，5 轮取最小（ms）。

   | 规模 | `append_unsigned` | 整文件重写 + rename | 尾部追加 200 B + fsync |
   |---|---|---|---|
   | 8 MB（`8,389,335` B） | 38.720 | 6.949 | 1.196 |
   | 64 MB（`67,109,591` B） | 296.232 | 93.475 | 1.801 |

   结论：`append` 随文件大小线性（8→64 MB 约 7.7×），尾部追加基本恒定 ⇒ 支持 §16.5.3
   「只做尾部追加」的方向。整文件重写落盘比内存内 `append_unsigned` 快，两者口径不同
   （前者不含层构造与摘要），不可直接相减。

2. **鲁棒性**：1 层文件（1056 B）分别截掉 1 / 32 / 64 / 128 B，四档结果**完全一致**：
   `info` = OK、`load` = OK、`layers()` = 空链、`Store::get` 返回基文档旧值，
   **`check` 返回 `ok=true`「结论 通过」**且无任何尾部告警。

   结论：半截追加会**静默丢掉一次写入**，读端退回基文档；当时的 `check` 不报告。
   这实证了「不得写『能优雅退化』」。**可探测性缺口已修复**：`check` 第 6 步新增
   「找不到完整 Trailer 但段区之后还有字节」一档，四档复跑均 `ok=false`；
   回归用例见 `rust/amberice/tests/unsigned.rs`。读端行为未改，尾部恢复仍待设计。

3. **层数**：100 层、39,603 B，20 轮取最小（ms）：`load` 0.3209、
   `Store::value` 0.2837、`Store::get` 0.2300。

   结论：100 层时读当前值仍是亚毫秒，`compact` 阈值不能只看读耗时，应看
   文件体积与层数增长（§16.5.4 的「维护操作」口径不变）。

结果同步进 `ref/claims-audit.md §8`、`repo/ref/unfinished.md §12`；本节在裁决之后才改为结论。
