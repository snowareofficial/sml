# 版本命名规则：**版本号 = 功能集**（草案 v0.1 · 未定稿）

> 2026-11-04 与用户逐问敲定。用户原话：
> 「A 行」「ok」「版本号可以是功能集」「稳定前数字用不了」。
> 本文件只做**设计**，零代码改动；`IDEAS.md` / `TODO.md` 未动。

---

## 0. 一句话

**版本不是「序号」，是「一组特性的名字」。**（类似 Rust edition：`2018` / `2021` 是功能集的名字，
不是兼容性声明。）

⇒ 由此推出三条：

1. 版本之间**没有大小关系**，不需要 `>=` 比较 —— 判据永远是「这个特性在不在这套功能集里」；
2. **稳定前必须带 `dev` 标记**：开发期写 `@version 50 "camelia" dev`，定稿后去掉 `dev`（`@version 50`）；
3. 开发代号**不参与排序**，所以开发期的新语法只能靠**特性位**开（`@feature enable type.featag`），
   稳定后才把该特性写进对应版本的功能集里。

## 1. 字面形式（2026-11-04 用户定）

| 阶段 | 写法 | 含义 |
|---|---|---|
| **开发期（小版本）** | `@version 50 "camelia" dev` | `50` = **`5.0` 的连写**（大版本+小版本，不写点）；`"camelia"` = 这一代的代号；`dev` = 开发中 |
| **稳定版** | `@version 50`（或 `5.0`） | 取 5.0 这份功能集 |
| **稳定版 + 代号** | `@version 50 "camelia"` | 代号**永久保留**，与 `5.0` 是**双向映射**（见 §1.2） |
| **只写代号** | `@version "camelia"` | 等价 `5.0` —— 代号本身就是一个版本名 |

- **连写是规范形式**（`50`），点号 `5.0` 与 `vN` 一律作为**容错别名**接受；
- 已发布 `v1`–`v4` 永久合法 ⇒ 等价 `10` / `20` / `30` / `40`（亦即 `1.0`–`4.0`）；

| 现有写法 | 等价于（连写 / 点号） |
|---|---|
| `v1` / `1` | `10` / `1.0` |
| `v2` / `2` | `20` / `2.0` |
| `v3` / `3` | `30` / `3.0` |
| `v4` / `4` | `40` / `4.0` |

### 1.1 为什么要连写 `50`

不是因为 `5.0` 不能被词法接受（**实测 `@version 5.0` 能正常取到字面 `5.0`**），
而是：**版本字面量不该看起来像浮点数**。`5.0` 在值位置是 `Float`，
同一个字形在两种位置有两种读法是长期的解释负担；`50` 没有这个问题。

### 1.2 代号 ⇄ 数字：**永久双向映射**

用户 2026-11-04：「稳定后 dev 代号**永久保留**，映射的。」

| 方向 | 用法 |
|---|---|
| `"camelia"` → `50` | 文档写代号，实现按 `50` 取功能集 |
| `50` → `"camelia"` | 诊断/CHANGELOG/迁移工具回显人类可读的代号 |

⇒ 代号**不是别名而是等价名**：两者在**任何**入口都必须被接受，永不因「已稳定」而失效。
映射表与功能集表**同一处登记**（避免两处漂）。

## 1.3 生命周期：支持 → 移除（破坏性改动后）

用户在 2026-11-04 定的流程：

1. **稳定后**：代号与数字永久映射，长期可用；
2. **一旦该代出现破坏性改动**：该代号会在**后续版本的实现里被移除**（不再接受）；
3. 此时两件事必须发生：
   - **兼容性与迭代保障模块** ⇒ **报错**（明确告知「此版本集已移除」而不是含糊的「不支持」）；
   - **`smltools` 提供迁移工具** ⇒ 把旧文档升级到新写法。

⇒ 版本集的状态是**三态**：`Supported`（可用）/ `Removed`（报错 + 指向迁移工具）/ 不存在（`E-FEATURE-004`）。
⚠️ **`Removed` 与「从未存在」必须用不同的码**，否则用户分不清「我写错了」还是「我该迁移了」。

| 现有写法 | 等价于 |
|---|---|
| `v1` / `1` | `1.0` |
| `v2` / `2` | `2.0` |
| `v3` / `3` | `3.0` |
| `v4` / `4` | `4.0` |

## 2. 数据模型

现在是「平坦枚举 + `Ord` 比较」（`Version::V1..V4`，`strict_strings()` 里用 `self >= Version::V2`）。
改成「**标识 → 功能集**」的查表：

```text
一行 = { 数字, 代号, 状态, 功能集 }

{ 10, None,      Supported, baseline + bareword-string }   # 别名 v1 / "1" / "1.0"
{ 20, None,      Supported, baseline }                     # 别名 v2
{ 30, None,      Supported, baseline }                     # 别名 v3
{ 40, None,      Supported, baseline }                     # 别名 v4（差异在语法层，不在特性集）
{ 50, "camelia", Dev,       baseline + type.featag(opt-in)} # 开发期：新特性一律 opt-in
```

规则：

- **比较运算消失**：不再有 `v >= 2.0` 这种判据（实测全仓只有 `strict_strings()` 一处用它）；
- 特性仍然是**位**，版本只是「一整套默认位」⇒ `@feature enable/disable` 在这套位之上做**窄化**
  （既有规则：文档不能扩宽调用方给的范围）；
- `@version` 与 `@feature base` 共用同一张表、同一套字面量；
- **一行同时承载「数字 / 代号 / 状态 / 功能集」** —— 代号映射与功能集不可能漂（同处登记）；
- 状态三态：`Dev`（开发中，需 `dev` 标记）/ `Supported`（稳定可用）/ `Removed`（报错 + 指向迁移工具）。

## 3. 与 semver 的关系（别混）

| | 谁用 | 含义 |
|---|---|---|
| **包版本**（`0.6.9-dev.0`、`0.7.0`） | crates.io / 包管理器 | 兼容性承诺 |
| **SML 文档版本**（`40`、`50 "camelia" dev`、`"camelia"`） | 文档里的 `@version` | 功能集 |

两者**互不推导**：包版本升 MINOR 不代表文档版本升级，反之亦然。
（现状已如此：`swsml 0.6.x` 同时支持 `v1`–`v4` 四套文档版本。）

## 4.5 迁移工具（`smltools`）：**扫 / 应用** 两段式

用户 2026-11-04：「smltools 可以自动迁移，有扫、扫与应用等」。
⇒ 迁移分成**只报告**与**写回**两档，中间可以有人复核 —— 这是 `cargo fix` / `rustfmt --check` 那一挂的做法。

| 模式 | 干什么 | 写文件？ |
|---|---|---|
| **scan（扫）** | 列出「哪些文件、哪一行、命中哪条规则、会改成什么」 | ❌ 只报告 |
| **apply（应用）** | 按规则写回；**幂等**（连续 apply 两次，第二次零改动） | ✅ |
| **rules（列规则）** | 列出全部规则 id + 适用版本集 + 说明 | ❌ |

```text
smltools -i a.sml --migrate scan        # 默认档：只报告（可接 CI）
smltools -i a.sml --migrate apply       # 写回
smltools --migrate rules                # 列出规则
smltools -i a.sml --migrate apply --rule v50-version,b2-symbol-modifier   # 只跑指定规则
```

**设计约束**

1. **默认 scan**：不显式 `apply` 就绝不改文件（与 `smltools` 现有「输出到 stdout / 显式落盘」的风格一致）；
2. **幂等**：apply 后再次 scan 必须为 0 命中，否则规则写错了；
3. **规则带 id 且可单跑**：CI 里可以只允许部分规则（避免一次大迁移糊成一团）；
4. **规则来源单一**：每条破坏性改动**附一条规则**，登记处与 CHANGELOG / `errors/codes.sml` 同源，
   不许两处手抄；
5. **与兼容模块联动**：`Removed` 报错时直接给出「该跑哪条规则」（错误文案带规则 id）。

⚠️ **现状**：`smltools` 是**扁平 flag 风格**（`-i` / `--to` / `--feature` / `--toc`，**没有子命令**）
⇒ 迁移建议做成 `--migrate <scan|apply|rules>`，而不是引入子命令体系（否则要重构 clap 结构）。
