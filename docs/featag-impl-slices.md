## 2. 键名白名单（S1，用户 2026-11-04：白名单策略）

| 允许 | 说明 |
|---|---|
| `A-Z` `a-z` `0-9` | ASCII |
| `_` `-` | 下划线与连字符（路径分隔只用 `.` 与 `[]`，不与它们冲突） |
| **CJK 统一汉字**（U+4E00–U+9FFF） | 中文键名是既有能力（`svg`/`slint` 会被 sanitize，但数据层允许） |
| **Kana**（U+3040–U+30FF）、**Hangul**（U+AC00–U+D7AF） | 日 / 韩键名（2026-11-04 用户定「可补」） |

| 拒绝 | 理由 |
|---|---|
| `.` `[` `]` | 路径语法保留 |
| 空白 / 控制字符（Cc） | 不可见 |
| **格式字符 / 零宽 / 双向控制（Cf）** | 不可见、可伪造显示 |
| **西里尔 / 希腊等同形字母** | 同形字攻击（`а` vs `a`）—— 白名单天然排除 |
| 全角标点、兼容区字符 | 与半角混用会造成「看起来一样、比较不等」 |

### 2.1 同形字：**只允许一种字形**（用户 2026-11-04）

> 原话：「字形相似的字母只能有一种，**声明时**」「特别是英语、西里尔那种」。

- **检查点在声明处**：契约名、字段名、featag 名 —— 不只是数据键；
- 允许的字形：**ASCII 拉丁** + **CJK 汉字**；**西里尔 / 希腊 / 亚美尼亚**等一律拒（`а`(U+0430) 与 `a` 不可共存，直接不允许前者出现）；
- ⚠️ **实现要求**：白名单是**字符范围表**，必须**生成到五端**（像码表那样），不许各端手抄范围 —— 否则「哪端放到多宽」迟早不一致。

### 2.2 带音标的拉丁字母：**做成 feature**，且开启后「单一语种」

> 用户 2026-11-04：「`é` 作 feature，开好就只能单一语种」。

| 项 | 决定 |
|---|---|
| 开关 | 独立**特性位**（候选名 `lex.latin-ext`，与既有 `lex` 域一致），**默认关** |
| 关闭时 | 只允许 ASCII 拉丁 + CJK 汉字（现行白名单） |
| 开启后 | 额外允许**预组合**的拉丁扩展字母（`é` `ü` `ç` `ñ` …） |
| **单一语种约束** | 开启后，**标识符层只能有一种文字系统**（Latin **或** Han），混用 ⇒ 报错。这正是同形字风险的机制化解法 |

💡 **关键：仍然零依赖。** 只要规定「只接受**预组合码位**（如 `é` = U+00E9），**一律拒绝组合标记（Mn/Mc）**」，
那么 NFC 就自动成立 —— 不需要归一化库，也不需要 Unicode 数据表，五端各写一段范围判断即可。

补充白名单（用户 2026-11-04：K6「可补」）：

| 补充范围 | 用途 |
|---|---|
| `Kana`：U+3040–U+30FF（平假名 / 片假名） | 日文键名（原先「Han 可以、假名不行」的缺口） |
| `Hangul`：U+AC00–U+D7AF（谚文音节） | 韩文键名 |

**「单一语种」的粒度 = 每个契约统一**（用户 2026-11-04 选 ②）：

- **一个契约内部的标识符**（字段名 / featag 名）必须同属一种文字系统；
- 不同契约可以用不同语种；
- **只作用于标识符**（键名 / 契约名 / featag 名），**值与正文不受影响**；
- 理由：同形字的危害发生在「同一个命名空间里两个看起来一样的名字」，而契约就是那个命名空间。

⚠️ 该规则不只服务 featag ⇒ 定稿后应**独立成 `docs/identifiers.md`**（键名 / 契约名 / featag 名 / 特性名共用一套）。
本轮先记在这里，避免再造一份还没定完的文档。
